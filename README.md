# Hunter

Hunter 是一个多人协作开发的 2D 横版撤离游戏项目，长期目标为服务端权威的 PvPvE。**本次参赛版采用 Unity 客户端＋C++ 本地服务端，通过 `127.0.0.1` 通信，先完成单人 PvE 撤离 Demo。**

玩家操作猎人进入地图，通过探索、战斗和击杀 Boss 获取战利品，在风险中选择继续探索或撤离。参赛版先验证动作体验与局内风险循环，赛后再扩展跨设备玩家遭遇和长期成长。

当前处于项目初始化阶段，仓库仅建立职责目录，尚未包含可运行的客户端、服务端或工具。本文说明项目目标与协作边界，具体玩法、协议和实现方案在后续开发中由相关成员共同确认。

## 参赛安排

本项目计划参加 TapTap「2026 聚光灯 21 天游戏创作挑战」。详见 [赛事时间与逐日开发计划](docs/2026-TapTap-GameJam-Plan.md)。

本机客户端/服务端分工已确认，参赛包包含两个进程，游戏自动启动和关闭本地服务端，全流程不依赖互联网、局域网或外部数据库。人数、工时和平台仍按时间规划中的假设估算。

官方不允许参赛游戏带有联网功能，但未明确解释本地回环通信；主办方是否接受该实现仍待确认，技术方案选定不代表官方已认可。来源：[官方活动细则](https://www.taptap.cn/poster/NIKiDS1YShdA)。

## 项目目标

1. **流畅的动作体验**：实现横版移动、跳跃、射击和受击，在本机双进程下验证输入响应、权威状态与画面反馈。
2. **完整的撤离循环**：参赛版连接探索、普通怪、Boss、战利品与撤离；多人争夺作为赛后扩展目标。
3. **一致的结果与存档**：由本地服务端裁定死亡、拾取与撤离并保存结果；重复请求、进程异常和重启不重复累计奖励。本地存档不承诺防篡改，远程资产安全赛后另行验证。
4. **清晰的多人协作边界**：客户端、服务端、策划与美术各自负责对应产物，通过统一协议、配置数据和联调验收协作。

参赛版首个可验证目标是：**一张灰盒地图、一把枪、一个 Boss、一名玩家、一次由本地服务端提交的结算**。之后再扩展双玩家与多人 PvPvE，不将完整长期系统塞入比赛排期。

## 基本约定

- **客户端使用 Unity，由客户端成员负责。**
- **服务端使用 C++，作为随包本地进程运行，由服务端成员负责。** 首版采用回环 TCP＋Protobuf，具体依赖与接口在开题初期验证并冻结。
- 客户端负责输入、预测和表现；服务端决定合法位置、命中、伤害、死亡、物品归属及撤离结果。
- 实时战斗以内存模拟推进，资产与结算通过持久事务处理，战斗 Tick 不等待数据库提交。
- 客户端先按权威快照平滑展示，预测按实际手感需要逐步增加；不预设 Unity 必须接入 C++ 原生库，双方必须对齐运动、碰撞与地图数据。
- 本地服务端仅监听 `127.0.0.1`，比赛包不提供远程连接或局域网发现入口；启动、暂停、异常退出及清理由两端共同验收。
- 本地存档由服务端单一写入，发布包无需额外安装数据库服务；不照搬完整分布式部署。
- 撤离条件、死亡损失与进程故障后的未完成对局处理由策划和相关开发成员共同确认。

## 目录结构

```text
Hunter/
├── client/       # Unity 客户端工程
├── server/       # C++ 本地服务端工程
├── design/       # 策划规则、关卡设计、数值与配置源表
├── art/          # 美术源文件与交付资源
├── protobuf/     # 客户端与服务端共用的 Protobuf 协议定义
├── export/       # 导表工具、校验规则与导出流程
├── docs/         # 跨团队接口、协作、联调与部署文档
└── README.md     # 项目目标、目录用途与职责说明
```

`docs/` 已包含参赛规划，其余模块仅保留目录占位，内部结构随实际需求建立。协议代码和配置数据的生成位置由双方约定，生成产物不得作为源文件手工维护。

## 职责分工

| 方向 | 主要目录 | 负责内容 | 主要交付 |
| --- | --- | --- | --- |
| 客户端 | `client/` | Unity、输入、镜头、表现、UI、回环协议接入、快照展示、本地服务端启动/退出管理 | 可运行客户端与完整发布包、资源规范、双进程联调结果 |
| 服务端 | `server/` | C++ 本地宿主、Tick、权威运动和战斗、AI、掉落与撤离、幂等结算、本地存档及异常处理 | 随包可执行文件、协议样例、服务端配置、构建与测试结果 |
| 策划 | `design/` | 游戏循环、系统规则、关卡、数值、配置源表、体验目标与验收场景 | 可执行的规则说明、配置数据、地图和资源需求 |
| 美术 | `art/` | 角色、场景、动画、特效与 UI 视觉资源；按约定制作和交付 | 美术源文件、运行时资源、命名与规格说明 |
| 协议协作 | `protobuf/` | 客户端与服务端共同维护本机会话、输入、快照、交互、暂停、结算和兼容性约定 | `.proto` 文件、C#/C++ 生成约定、样例与变更说明 |
| 导表协作 | `export/` | 服务端成员主责工具与校验；策划维护源表，客户端负责接入并共同确认格式 | 可重复执行的导表流程、校验结果、双方所需配置产物 |
| 公共文档 | `docs/` | 共同维护接口契约、技术决策、环境说明、联调记录与发布流程 | 能供其他成员理解、接入和复现的协作资料 |

每个模块和跨模块任务需要明确一名负责人及相关评审人，具体成员在认领时补充。公共目录由参与方协作维护，变更需让受影响的使用方知情并参与确认。

## 共同协作边界

### Protobuf 协议

`protobuf/` 是跨端消息定义的统一来源。客户端与服务端在开发前共同确认字段含义、请求与响应关系、错误码、本次启动会话的关联方式、序号、重试语义和版本兼容方式。比赛期生成 C# 和 C++ 代码，按回环 TCP 分帧传输；不排入在线账号与匹配协议。

Protobuf 用于描述消息结构，不代替传输、认证、分帧或可靠性设计。两端使用约定的生成方式接入，不以某一端私有结构作为另一端的隐式接口。已使用的字段编号不能随意更改或复用，协议变更应同步更新样例和联调记录。

### 策划配置与导表

配置流转按以下方向组织：

```text
design/ 中的配置源表
    → export/ 中的导表与校验工具
    → 客户端配置产物 / 服务端配置产物
    → 双方加载并验证配置版本
```

策划负责数据含义、数值和内容；工程成员负责字段类型、必填项、ID 唯一性、引用关系及范围校验。配置按客户端表现和服务端规则分别导出；参赛包包含两端运行所需数据，本地打包不提供数据保密保证，远程版本再单独定义下发范围。

涉及战斗规则的配置需具备版本标识。同一场对局使用固定的配置版本，具体导出格式、产物目录和发布方式在接入前共同确定。

### 美术与客户端

美术与客户端在制作前确认尺寸、比例、坐标基准、命名、动画状态、导出格式和资源预算。美术负责按规范交付，客户端负责资源导入、运行时组织和表现接入，策划参与效果验收。

地图外观与权威碰撞数据需要共同校验。出生点、Boss 点、撤离点和交互位置应形成服务端可使用的数据，不能只存在于客户端场景表现中。

### 服务端与客户端联调

双方先验证服务端自动启动、端口交付、协议/内容版本握手，再对齐坐标、单位、Tick、运动和地图碰撞，逐步接通输入、快照、交互、暂停与结算。客户端可以立即表现操作反馈，正式结果以服务端已提交的结算为准；暂停时服务端也需确认停止模拟和计时。

完整验收必须使用 Unity 和真实本地服务端。除玩法外，还需检查端口占用、启动超时、进程强退、存档异常、多开策略、退出残留，以及在没有开发环境的 PC 上断网一键运行。两端构建、协议和配置版本随每日发布包一起记录。

## 初期推进顺序

| 阶段 | 主要成果 | 验收重点 |
| --- | --- | --- |
| 规则与本机接入 | 最小玩法、启动与握手、Protobuf、配置与地图契约 | 10/1 双进程握手可用，接口和状态归属清楚 |
| 本机动作切片 | Unity 输入/表现、C++ 运动/战斗、导表、自动开服与组包 | 10/4 干净 PC 断网完成一次短战斗 |
| PvE 撤离闭环 | Boss、掉落、死亡、撤离、服务端本地存档 | 10/7 从启动到结算可玩，重复请求和重启结果正确 |
| 冻结与发布 | 试玩、异常处理、资源完善、提交材料与审核 | 10/12 功能冻结，10/17 首次上传，10/20 核查有效投稿 |
| 赛后 PvPvE | 双玩家、远程传输、认证、预测校正、资产安全与长期成长 | 单独规划和验证，不视为修改连接地址即可完成 |

参赛版首个端到端验收场景：断网启动游戏 → 自动启动本地服务端 → 玩家进入地图 → 击杀 Boss → 拾取并撤离 → 服务端保存结算 → 重复查询结果不重复累计 → 退出后无服务进程残留 → 再次启动仍可读取已确认结果。另测死亡重开、服务端异常退出和保存失败。

任务以具体可验收成果拆分，写清负责人、修改目录、前置依赖、失败场景和验证方式。跨模块接口先达成约定，再并行实现；阶段是否完成以可复现的结果为准。

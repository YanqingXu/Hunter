# Hunter

Hunter 是一个多人协作开发的 **2D 横版、服务端权威的 PvPvE 撤离游戏**。

玩家操作猎人进入地图，通过探索、战斗和击杀 Boss 获取战利品，在其他玩家与环境威胁下选择继续争夺或撤离。项目围绕动作体验、局内风险与局外成长建立完整游戏循环。

当前处于项目初始化阶段，仓库仅建立职责目录，尚未包含可运行的客户端、服务端或工具。本文说明项目目标与协作边界，具体玩法、协议和实现方案在后续开发中由相关成员共同确认。

## 项目目标

1. **流畅的动作体验**：实现横版移动、跳跃、射击、受击等基础操作，并在真实网络环境下验证预测、同步与反馈。
2. **完整的 PvPvE 撤离循环**：将探索、怪物、Boss、玩家遭遇、战利品争夺与撤离连接成一局可重复体验的游戏。
3. **可信的资产结果**：由服务端裁定死亡、拾取与撤离，保证带入、带出、损失和奖励在重试、断线及服务故障下不会重复生效或复制装备。
4. **清晰的多人协作边界**：客户端、服务端、策划与美术各自负责对应产物，通过统一协议、配置数据和联调验收协作。

首个可验证目标是：**一张灰盒地图、一把枪、一个 Boss、两名玩家、一次可靠结算**。完成这个闭环后，再逐步扩展队伍、武器、道具、猎人特质与成长体系。

## 基本约定

- **客户端使用 Unity，由客户端成员负责。**
- 服务端按 C++ 权威模拟方向推进，负责游戏规则执行和持久业务；具体依赖、工具链与传输方案在验证后确定。
- 客户端负责输入、预测和表现；服务端决定合法位置、命中、伤害、死亡、物品归属及撤离结果。
- 实时战斗以内存模拟推进，资产与结算通过持久事务处理，战斗 Tick 不等待数据库提交。
- 客户端是否复用服务端模拟代码另行评估，不预设 Unity 必须接入 C++ 原生库；双方必须对齐运动、碰撞和地图数据规则。
- 具体死亡损失范围、友伤、撤离条件、断线时限与故障补偿规则由策划和相关开发成员共同确认。

## 目录结构

```text
Hunter/
├── client/       # Unity 客户端工程
├── server/       # 服务端工程
├── design/       # 策划规则、关卡设计、数值与配置源表
├── art/          # 美术源文件与交付资源
├── protobuf/     # 客户端与服务端共用的 Protobuf 协议定义
├── export/       # 导表工具、校验规则与导出流程
├── docs/         # 跨团队接口、协作、联调与部署文档
└── README.md     # 项目目标、目录用途与职责说明
```

各目录当前为空，内部结构随实际需求建立。协议代码和配置数据的生成位置由双方约定，生成产物不得作为源文件手工维护。

## 职责分工

| 方向 | 主要目录 | 负责内容 | 主要交付 |
| --- | --- | --- | --- |
| 客户端 | `client/` | Unity 工程、输入、镜头、动画与音效接入、UI、会话接入、预测校正、插值与重连 | 可运行客户端、资源接入规范、客户端联调结果 |
| 服务端 | `server/` | 身份与会话验证、房间与对局、权威运动和战斗、AI、掉落与撤离、资产结算与恢复 | 可运行服务、联调环境、接口行为说明与测试结果 |
| 策划 | `design/` | 游戏循环、系统规则、关卡、数值、配置源表、体验目标与验收场景 | 可执行的规则说明、配置数据、地图和资源需求 |
| 美术 | `art/` | 角色、场景、动画、特效与 UI 视觉资源；按约定制作和交付 | 美术源文件、运行时资源、命名与规格说明 |
| 协议协作 | `protobuf/` | 客户端与服务端共同维护消息、字段、枚举和兼容性约定 | `.proto` 文件、生成约定、协议样例与变更说明 |
| 导表协作 | `export/` | 工程成员维护导表工具和校验，策划维护源表及字段含义，客户端与服务端确认消费格式 | 可重复执行的导表流程、校验结果、双方所需配置产物 |
| 公共文档 | `docs/` | 共同维护接口契约、技术决策、环境说明、联调记录与发布流程 | 能供其他成员理解、接入和复现的协作资料 |

每个模块和跨模块任务需要明确一名负责人及相关评审人，具体成员在认领时补充。公共目录由参与方协作维护，变更需让受影响的使用方知情并参与确认。

## 共同协作边界

### Protobuf 协议

`protobuf/` 是跨端消息定义的统一来源。客户端与服务端在开发前共同确认字段含义、请求与响应关系、错误码、身份绑定、序号、重试语义和版本兼容方式。

Protobuf 用于描述消息结构，不代替传输、认证、分帧或可靠性设计。两端使用约定的生成方式接入，不以某一端私有结构作为另一端的隐式接口。已使用的字段编号不能随意更改或复用，协议变更应同步更新样例和联调记录。

### 策划配置与导表

配置流转按以下方向组织：

```text
design/ 中的配置源表
    → export/ 中的导表与校验工具
    → 客户端配置产物 / 服务端配置产物
    → 双方加载并验证配置版本
```

策划负责数据含义、数值和内容；工程成员负责字段类型、必填项、ID 唯一性、引用关系及范围校验。客户端和服务端需要的数据可以分别导出，服务端私有数据不应默认打入客户端。

涉及战斗规则的配置需具备版本标识。同一场对局使用固定的配置版本，具体导出格式、产物目录和发布方式在接入前共同确定。

### 美术与客户端

美术与客户端在制作前确认尺寸、比例、坐标基准、命名、动画状态、导出格式和资源预算。美术负责按规范交付，客户端负责资源导入、运行时组织和表现接入，策划参与效果验收。

地图外观与权威碰撞数据需要共同校验。出生点、Boss 点、撤离点和交互位置应形成服务端可使用的数据，不能只存在于客户端场景表现中。

### 服务端与客户端联调

双方优先对齐坐标、单位、Tick、运动和碰撞规则，再验证登录、房间、输入、快照、重连及结算。客户端可以立即表现操作反馈，但正式资产结果以服务端已提交的结算为准。

联调使用同一套协议与兼容的配置版本，记录复现步骤、网络条件和结果。服务端测试工具可用于提前开发，完整阶段验收仍需要真实 Unity 客户端参与。

## 初期推进顺序

| 阶段 | 主要成果 | 验收重点 |
| --- | --- | --- |
| 规则与接口准备 | 最小玩法、职责认领、协议、配置与地图契约、开发环境 | 各方知道输入输出、状态归属与失败处理方式 |
| 动作切片 | Unity 灰盒、基础运动、一把枪、服务端模拟 | 跑跳射击可操作，双方运动规则可对照验证 |
| 双客户端联网 | 权威对局、输入与快照、预测校正和重连 | 两个独立客户端在受控网络条件下完成对战 |
| PvE 撤离与资产闭环 | Boss、掉落、死亡、撤离、带入锁定及持久结算 | 从入局到结算完整可运行，重试和重启不复制资产 |
| 内容与发布扩展 | 更多玩家、队伍、武器和成长；部署与稳定性建设 | 根据试玩结果逐项扩展并完成对应验收 |

首个端到端验收场景：A、B 带入装备进入同一地图，击杀 Boss 后 A 死亡，B 拾取并撤离；重复提交 B 的结算并重启服务后，A 的死亡结果保持，B 的奖励只发一次，所有装备实例没有复制。

任务以具体可验收成果拆分，写清负责人、修改目录、前置依赖、失败场景和验证方式。跨模块接口先达成约定，再并行实现；阶段是否完成以可复现的结果为准。

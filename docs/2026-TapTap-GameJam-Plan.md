编制日期：2026-09-21。状态：参赛排期草案，人员、投入时长、平台和离线参赛范围待团队确认。

## 1. 赛事信息与本项目的关键冲突

本届为 TapTap 主办的第三届线上 GameJam，围绕开题公布的主题创作可玩作品，包含开发、试玩评审及后续颁奖环节。报名由队长发起，再邀请队员加入。来源：[官方报名公告](https://www.taptap.cn/moment/843821543216645719)。

| 官方节点 | 日期/时间 |
| --- | --- |
| 报名 | 2026-09-01～09-30 |
| 主题公布、开发开始 | 2026-10-01 12:00 |
| 上传、通过审核并完成投稿的截止 | 2026-10-21 12:00 |
| 官方建议上传时间 | 10 月 18 日前 |
| 试玩评审 | 2026-10-25～12-03 |
| 获奖名单公布 / 公示阶段 | 2026-12-10 / 12-10～12-25 |
| 线下颁奖 | 2027 年 1 月，具体日期待公布 |

来源：[官方活动页：日程、活动细则与 Q&A](https://www.taptap.cn/poster/NIKiDS1YShdA)。官方使用“21 天”名称，但上述起止时刻相隔 20×24 小时；本计划按 10/1～10/21 的 21 个日历日期编号，首末日不当作完整工作日。

**活动页明确不允许参赛游戏带有联网功能。** 当前 Hunter 的联网 PvPvE 目标与此冲突。因此建议参赛包改为 Unity 离线 PvE 撤离 Demo，保留探索、Boss、战利品与撤离，联网方向留待赛后。不能将本地开服、回环连接或需要登录的游戏当作已经符合离线要求的替代方案。来源：[官方活动页 Q&A](https://www.taptap.cn/poster/NIKiDS1YShdA)。

这是范围调整建议，尚不表示团队已批准修改长期目标。队长应在 9/23 前向主办方核实疑问并记录答复；未获得明确例外前，不把联网能力排入参赛交付。若团队坚持联网版本，应重新决定参赛安排，而不是按原方案压缩赶工。

主题目前尚未公布，不能提前认定现有猎人设定符合命题。赛前仅安排组队、环境、流程、参考和素材授权准备；已有代码/素材的可用范围另向主办方核实，记录来源与创建时间，不将既有作品直接视为本次限时新作。

| 局长 | 首次完整体验约 5～8 分钟 | 两轮外部试玩后调整 |
| 分工补充 | 策划兼队长/发行；全员分担测试；服务端成员在比赛期承担逻辑/工具 | 不假设另有专职 QA、运营或音频成员 |

以 10/1～10/16 的 16 个日历日期粗算，每人约 64～96 小时，两名工程成员合计约 128～192 小时；首日半天和实际缺勤另扣。最多安排其中 75% 给确定任务，其余用于集成、返工和故障处理。不能把美术或策划工时直接算成可替代的工程产能。

若工程成员平均每天不足 4 小时，优先缩小玩法范围：保留一张小地图、一种攻击、一个可读招式的 Boss 和一次撤离；减少普通怪数量，取消成长、复杂背包和可选内容。若服务端成员不熟悉 Unity/C#，先负责导表、构建、存档验证与测试，不能按第二名成熟 Unity 开发者估算进度。

## 3. 参赛范围与角色职责

### 3.1 参赛包最小范围

| 必须完成 | 控制规模 |
| --- | --- |
| 主题表达 | 开题后选一个与核心操作直接相关的主题机制，玩家可在前 2 分钟感知 |
| 操作与战斗 | 跑、跳、瞄准、射击、换弹、受击、死亡；一把枪 |
| 地图 | 一张小型固定地图，少量分支，一种普通怪，一个 Boss |
| 风险与撤离 | 拾取战利品，选择继续冒险或撤离；失败与成功结果清晰 |
| 最小结果与存档 | 当局成功/失败、带出数量、累计记录；本地结算不重复应用 |
| 基本可用性 | 标题、开始、操作提示、暂停/音量、结算、重开、退出 |
| 发布产物 | 可运行安装/压缩包、说明、页面素材、演示与实机视频、素材来源记录 |

比赛期不排入：联网 PvP、匹配、账号系统、云存档、远程数据库、完整永久猎人资产经济、复杂特质、转生、自由地形破坏、双端适配。这里的本地存档可靠性不等同于赛后服务端资产可信性。

可选项仅在 10/12 之前、所有必做项已验收且至少有 1 天余量时考虑：一个补给道具、Boss 第二种攻击、简单环境反馈。任何可选项不延迟首次上传。

### 3.2 比赛期间的分工

| 角色 | 主责 | 与他人的接口 |
| --- | --- | --- |
| 客户端 C | Unity 工程、角色控制、相机、表现、UI、场景接入、出包 | 接入逻辑模块、配置及美术，维护每日可玩包 |
| 逻辑/工具 T（原服务端成员） | 纯本地战斗/AI/掉落逻辑、结果与存档、导表、自动检查、构建辅助 | 与 C 提前冻结 C# 数据与调用契约；不强制移植 C++ 平台 |
| 策划/队长 D | 开题取舍、数值和地图、测试招募、任务裁剪、日志、页面与投稿 | 每天提供规则与验收，不等到最后验收整体体验 |
| 美术 A | 风格、角色/场景/怪物、UI 与反馈素材、封面截图 | 按冻结规格分批交付，先能接入再做精修 |

`server/` 和 `protobuf/` 保留为长期工程目录，本次不投入网络协议与服务器开发。离线模块在 `client/` 内协作；导表工具在 `export/`，源表在 `design/`，源资源在 `art/`，规范与验收记录在 `docs/`。不为了沿用目录而增加进程、网络或序列化层。

## 6. 关键依赖与减项规则

```text

  → Boss/掉落/撤离/结算完整（10/7）
  → 外部试玩与必做项完成（10/12）
  → 回归、素材和候选包（10/16）
  → 上传、审核、活动投稿（10/17～10/20）
```

| 检查点 | 未通过时的立即行动 |
| --- | --- |
| 10/1 18:00 还没有明确主题玩法 | 选最小的一个主题机制；舍弃需要多个新系统配合的方案 |
| 10/4 战斗操作仍不可用 | 停止装饰与扩展；降低平台跳跃复杂度、怪物行为和动画数量，保留必要攻击反馈 |
| 10/7 无完整循环 | 固定掉落、固定撤离点、单一 Boss 招式；取消复杂背包与成长；全工程力量接通起终点 |
| 10/10 存档尚不稳定 | 只保存已完成局的简短结果，取消跨局装备流转；必要时改为单局无长期存档并修改页面说明 |
| 10/12 必做项仍有缺口 | 删除全部可选项；10/13～10/14 只补闭环和致命问题，不增加新场景 |
| 10/15 材料缺失 | 队长与美术优先补提交材料，工程仅保障可录制构建；不能用计划功能代替实机演示 |
| 审核提出问题 | 优先修该问题和必要回归；暂停性能微调、可选美化和架构整理 |

减项后仍必须保留题目相关的核心机制、完整起终点和明确反馈。任何改变主要玩法的裁剪由队长、策划和客户端负责人当天确认，并同步材料。

## 7. 每日协作与检查方式

- 每人开始工作前用 10 分钟同步当天交付与阻塞；跨角色接口问题当天解决，不等周会。
- 按每人约 5 小时安排：约 3 小时主任务、1 小时集成/修复、30 分钟试玩、30 分钟记录与沟通。每日同步包含在沟通时段内。
- 20:30 前合入当日可用改动；21:00 出包；21:30 全员玩同一版本并记录结果。无法符合该时段时，9/22 一次性对齐全队固定交集。
- 主分支每日可构建。未完成任务保留在各自分支，不让占位功能阻塞其他成员的可玩版本。
- 10/4 起每日保留版本号、提交、配置版本、可玩包位置和已知问题；10/12 后每个修复附复现步骤与回归结果。
- 每张任务卡写负责人、前置依赖、目录、完成条件和预计小时；超过 1 天的任务拆成能演示的子任务。

最低检查集：断网启动；新玩家完成一局；死亡重开；撤离重开；重复点击结算不重复累计；退出重进；保存失败给出可理解处理；不依赖开发机路径；连续 10 局无阻塞。性能目标和测试设备在 10/4 前记录，避免临近提交才临时扩大适配范围。

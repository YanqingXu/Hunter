## E. SQLite 接入、结算与异常恢复

这部分**不是重新实现 SQLite 模块**。

已有 `Storage` 支持异步打开、加载玩家、分配持久对局 ID、提交结算、查询结果和停止，并具备事务与去重约束；目前主要缺少与真实游戏流程的接通。

| 编号      | 基础任务               | 第一版完成标准                                                        | 类型      |
| ------- | ------------------ | -------------------------------------------------------------- | ------- |
| **D17** | **启动与玩家存档加载接通**    | 宿主准备存档路径并打开 Storage，成功加载本地玩家与永久物品后才能进入可开局状态；失败明确提示，不静默清档       | 新增接入    |
| **D18** | **开局使用持久 MatchId** | 调用 `alloc_match()`，成功完成后才创建活动对局；重启后不复用旧对局 ID，不能继续只依赖内存自增       | 调整      |
| **D19** | **结算编排与结果查询**      | 服务端生成并冻结结算请求，提交后进入保存中；确认已提交才展示成功；重复请求返回原结果，提交状态未知时查询或按原请求重试    | 新增      |
| **D20** | **恢复、失败与退出收尾**     | 重启加载最后已提交结果；未完成局不发奖；损坏/未知版本存档保留原文件；退出时按既有 Storage 契约排空已接受任务和回调 | 新增接入＋复用 |

### 第一版必须守住的结算顺序

```text
服务端确认本局结果
    ↓
冻结结算请求
    ↓
进入 Settling
    ↓
Storage 接受请求
    ↓
等待提交完成
    ↓
更新永久物品展示
    ↓
进入 Finished
```

**“请求已接受”与“奖励已保存”不是同一个状态。** 当前存储契约已经明确区分，接入时必须保留这一点。重试时也不能重新随机掉落、重新生成另一份奖励列表，或换一个 MatchId 再提交。

SQLite 的事务能力提供数据库层面的原子提交基础，但游戏仍需自行处理“提交成功后、通知客户端之前进程退出”的业务恢复路径。([SQLite][1])

### 多人数据库现在是否要重做？

**不需要为了预留联机，就立即推翻现有单人 V1 表结构。**

建议现在把业务入口设计为：

```text
提交某一局、某一玩家的结算
```

而不是：

```text
保存全局唯一玩家的结果
```

当前存储适配器仍可按一局一名玩家落库。真正增加多人结算时，再迁移为能容纳同一局多名参与者结果的结构。现有 `match_result` 以 `match_id` 为主键，这个后续迁移点需要记录清楚，不能宣称已经支持多人结果。

| ------- | -------------------------------------------- | ------------- | ------------- |
| 身份来源    | `resolve_local_profile()`                    | 返回本地存档玩家      | 增加远程认证来源      |
| 会话绑定    | `bind_session(session_id, player_id)`        | 只绑定一个会话       | 管理多个连接和玩家     |
| 世界与玩家查找 | `find_player(world_id, player_id)`           | 一个世界、一个玩家     | 多世界、多玩家索引     |
| 命令处理    | `handle_command(context, command)`           | 处理本地玩家命令      | 按会话路由到不同玩家    |
| 战斗目标选择  | `query_targets(world, source, filter)`       | 返回单人 PvE 合法目标 | 多玩家、阵营、范围筛选   |
| 快照构造    | `build_snapshot(world, viewer)`              | 完整单人可见快照      | 接入 AOI 和可见性裁剪 |
| 消息发送    | `send_to(session_id, message)`               | 发送给唯一连接       | 每会话独立队列与背压    |
| 结果提交    | `settle_player(match_id, player_id, result)` | 一局一名玩家        | 一局多名参与者分别结算   |

另外，暂停、断线、死亡结束等规则建议放在**单人模式策略**中。

例如：

```text
单人版：
玩家死亡 → 本局结束
客户端断开 → 中止本局
暂停请求 → 暂停世界

多人版：
玩家死亡 → 修改该玩家状态
客户端断开 → 按重连规则处理该玩家
暂停请求 → 根据多人模式决定是否允许
```

**现在只实现左边，但不要把左边写成底层网络或通用 World 的不可改变规则。**

需要特别说明：这些接口只能减少未来改造范围，**不意味着以后把人数从 1 改成 2 就能完成联机**。多人同步、重连、公网认证和多人资产结算仍然需要单独实施与验证。

# 四、明确哪些东西第一版不做

# 五、实际执行顺序

不建议按类名依次开发：“先 Entity，再 Player，再 Skill，再 Item”。应按能够验收的游戏切片推进。

| 阶段                 | 主要任务                                | 验收结果                              |
| ------------------ | ----------------------------------- | --------------------------------- |
| **阶段 1：接口边界与真实接入** | D01—D04，D22；并行启动 D25 的 Android 技术验证 | Unity 能进入现有战斗，输入、角色身份和消息接收关系明确    |
| **阶段 2：可完成的一局战斗**  | D05—D12，补充 D07 所需配置                 | 玩家可以进入地图、战斗、击杀 Boss，死亡和重开正确       |
| **阶段 3：撤离玩法闭环**    | D13—D16，扩展 D21、D23、D24              | 能拾取、装入背包、完成撤离并得到明确的局内结果           |
| **阶段 4：永久结果闭环**    | D17—D20，D29、D30                     | 撤离奖励可靠入库，重复结算不重复发奖，重启后结果一致        |
| **阶段 5：目标平台交付**    | 完成 D25—D28、D31、D32                  | Android 断网安装可玩，异常处理、暂停恢复和完整流程验收通过 |

**D25 的平台技术验证要早做；完整平台打包可以后做。** 这是为了尽早发现平台阻塞，而不是让客户端与玩法开发一直等待 Android 宿主完成。

# 六、Demo 完成的最终验收清单

下面这些都通过，才可以把第一版标记为完成：

| 场景             | 预期结果                      |
| -------------- | ------------------------- |
| 首次断网启动         | 自动建立本地服务实例和存档，能够进入游戏      |
| 一局正常游玩         | 可以跑跳、射击、受伤、击杀普通怪与 Boss    |
| 拾取与背包          | 物品数量正确，背包满有明确提示，重复请求不复制物品 |
| 撤离取消           | 离开区域或死亡后倒计时正确终止           |
| 成功撤离           | 只提交一次有效结算，永久仓库获得对应战利品     |
| 死亡或主动放弃        | 不获得本局未结算战利品，已有永久物品不丢失     |
| 结算重复请求         | 返回同一份已保存结果，不再次增加奖励        |
| 提交成功后客户端未收到结果  | 再次启动或查询能找回已提交结果           |
| 保存失败或状态未知      | 不显示虚假的保存成功，不通过新建请求重复发奖    |
| 暂停与恢复          | 游戏计时冻结，恢复不补放旧输入           |
| 连续重开与退出        | 不残留旧实体、旧计时器、旧回调或异常服务进程    |
| Android 真机离线运行 | 无开发环境也能从启动玩到结算，再次启动可读档    |

**对当前 Hunter，首版最重要的主线就是：**

> **保留已有战斗基础 → 收拢单人假设 → 补 Boss、掉落、背包和撤离 → 接通现有 SQLite → 用真实客户端和目标设备验证完整闭环。**

**多人预留做到“入口有身份、世界有归属、操作有上下文、消息有接收者、结算有参与者”即可，不需要先完成半套 MMO。**

### 共用实现约束

`Skill` 保存身份和展示信息，`SkillEffect` 保存明确的属性代码、运算和数值。
`Desc`、`EffectDesc` 和旧 `Attribute` 草稿不参与执行解析。`mul_bp=10000` 表示原值，
同属性固定增量与倍率增量分别汇总，再统一取整；缺失效果或超出有效范围时拒绝配置。
11/12/2 的上述数值可从现有描述确定，其他幅度与复活参数仍待策划补充。
14 的“额外 1 个”已明确，但箱子种类、奖励来源和满容量处理尚未明确。

数值被动技能复用 `game.skill` 的只读有效配置，效果接入已有移动、枪械和工具规则。
技能持有、已消费标记、死亡序号、动作计时和数量保存在 C++ 权威对象中。
新增跨 Tick 字段时同步 schema、桥接、状态导入、快照和版本；Lua 不另存可变状态副本。
箱子奖励的规则判断由 Lua 决定，数量变化与场景消费由原生批量提交，失败保持原状态。

客户端负责选择技能、复活请求、读条、图标、音效和结果展示。表中这些被动属性无需
各建一套 `SkillEditorKit` 时间轴；需要动画或特效的动作可复用该模块表现，
最终生命、弹药、治疗、携带量和奖励仍读取服务端结果。Unity 接入须独立联调验收。
当前 Unity 正式入口仍为本地“边境试炼”：技能调用、运动与受伤直接修改本地对象，
尚未接入 Hunter 的技能状态、配装和复活动作协议。现有检查点重生不能当作死灵法师实现；
上述技能选择、读条和数量展示均须纳入后续协议适配。
复用 `SkillEditorKit` 时须调整默认 `BeHit` 命中回调，仅呈现权威事件与快照，
避免当前本地扣血逻辑和服务端伤害重复结算。

### 实施顺序与验证

1. 优先整理已有 11 项效果的配置与独立验证入口。以已明确的医疗减半、治疗翻倍和
   满血复活表达固定效果；其余项目保留待填数值。测试数值与正式源表分开。
2. 推进不依赖掉落资源的规则：先明确非消耗品携带量，再接入货运骡子；
   明确奔跑体耗后接入精力充沛，建立听觉感知后接入猫步。各项先更新契约再实现。
3. 开箱大师先围绕独立奖励夹具验证交互完成、额外数量、重复请求及容量失败，
   在补充策划案给出箱子资源后接入正式奖励来源。
4. 按技能切片验收服务端和 Unity 表现，恢复完整生产来源后再做完整对局联调。

目前独立运行入口是 Lua 技能模块测试。现有 C++ Hunt 契约仍依赖完整的
`generated/content.json` 和脚本组装产物；新增原生状态或行为时，应补专用最小夹具入口，
不能把沿用旧生成内容的契约运行当作当前工作簿接入完成。

# Server 工作约定

## 当前阶段

本目录已实现 Windows 基础框架、基础战斗切片和两种 Luax 加载路径。设计基线见 [plan.md](plan.md)，
构建与运行见 [README.md](README.md)，验证范围见 [VERIFICATION.md](VERIFICATION.md)。

- `.gitkeep` 仅用于保留空目录。
- `lua/main.lua` 组装会话、世界、移动、战斗和 AI；未列入清单的掉落与结算文件仍是占位。
- `lua/modules.json` 定义正式构建清单，桥接与状态 schema 见 `lua/contract.json`。
- 不因目录和文件已经存在，就将相应阶段、模块或测试标记为完成。

## 后续开发流程

收到具体实现任务后，按以下顺序工作：

1. 阅读 `plan.md`，确认任务范围和前置依赖。
2. 在 `intents/` 中建立或更新对应设计契约，从 [规则入口](rules/README.md) 阅读适用规则。
3. 明确不变量、线程与所有权、接口、失败行为和验证入口。
4. 根据契约补充有意义的测试，再实现并记录验证结果。

现有 intent 的 active 仅覆盖其当前实现范围，draft/deferred 不能视作已实现。
Android 工具链与真机、Unity 联调仍待验证，不得将延期内容自动加入当前任务。

`rules/` 已收录编码原则、排版、可读性、短类型命名和重构约定；其中的规则编号用于评审引用，
不代表已有自动检查器。文档中的示例不定义正式接口，具体契约以规划与对应 intent 为准。

## 目录与协作边界

- `src/` 放共用 C++ 核心，`platform/` 放 Android 与桌面宿主适配；头文件与实现文件按模块放在同一目录，不建立独立的 `include/` 目录。
- 所有服务端自有 C++ 代码统一使用 `src/common/Types.h` 中的短类型名，第三方库除外；包括平台适配、测试和工具。具体映射、直接包含要求及外部接口边界见 [短类型命名规则](rules/type_naming_rules.md)。
- 项目自有 C++ 与 Lua／Luax 的类、函数、文件、变量、参数等所有命名必须简洁且可读，统一使用 `Cfg`／`cfg` 等明确缩写；范围、词表和契约边界见 [可读性规则](rules/readability_rules.md) 的 `R-READABILITY-01`。
- 所有自有代码必须有中文注释：文件开头说明职责与作用，所有具名函数声明前一行写中文说明，
  无独立声明时写在定义前；简单函数一句即可，必要调用约束必须说明。函数体内默认不写步骤性
  注释，允许就近解释命名与结构无法充分表达的局部原因；匿名函数与回调按需说明约束。
  禁止英文说明句，工具指令保留要求的原文与位置；具体见
  [可读性规则](rules/readability_rules.md) 的 `R-READABILITY-02`、`R-READABILITY-08`、`R-READABILITY-09`。
- `lua/main.lua` 负责组装和入口分发，玩法放在 `lua/game/`，通用脚本支持放在 `lua/framework/`。
- `tools/` 放服务端专用脚本与制品工具；通用导表继续使用仓库根目录 `export/`。
- 协议继续使用根目录 `protobuf/`，配置源表使用 `design/`，不建立重复来源。
- 正式发布面向 Android 随包双进程，Windows 用于开发；Luax 的线程、重入、模块授权和数据边界以规划及固定候选的实际接口为准。

## 验证与进度

目录、注释或规划调整只检查相应结构、格式与引用，不要求编写业务测试。后续实现运行与改动相关的契约和集成验证；Android 行为必须包含真机证据，不能以 PC 通过代替。

进度说明区分已规划、已实现和已验证，记录实际执行结果，不将占位文件或未运行的测试作为完成证据。

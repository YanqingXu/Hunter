结合 Hunter 当前的实现，我最推荐的方向是：

> **用 `Entity → Unit → Player / Monster` 表达局内对象的概念关系；实际采用“纯数据状态＋功能模块”的组合方式。`Skill`、`Item`、`Equip` 不要全部塞进 `Entity` 的继承树。**

还有一个与你仓库直接相关的前提：**这些玩法类型应优先放在 Luax 层，而不是再建立一套 C++ 战斗类。** 当前规划明确要求实体、位置、血量、局内物品等只在脚本中维护一份权威状态，C++ 负责宿主、通信、调度和后续存储支持。

下面的建议基于本次读取到的 `main` 提交 `70b0dce`，重点面向你现在的单人 PvE 撤离 Demo，同时为后续 PvPvE 保留必要边界，不提前引入完整 MMO 框架。

## 一、先看现在的代码，哪些地方值得拆

目前 `world.lua` 的 `actor()` 已经承担了基础角色构造：玩家和怪物使用同一张表，包含位置、速度、血量、弹药、换弹、AI 和攻击冷却；同时，多处通过 `world.entities[1]` 获取玩家，通过后续数组位置对应怪物出生配置。

这对当前灰盒战斗切片是可用的，但继续扩展时，建议优先处理下面几个问题：

| 当前做法                                         | 扩展时容易遇到的问题           | 建议方向                     |
| -------------------------------------------- | -------------------- | ------------------------ |
| 玩家和怪物都拥有 `ammo`、`ai` 等字段                     | 对象不断增加“不适用于自己”的状态    | 公共状态保留，枪械、AI 等按能力组合      |
| 玩家固定在 `entities[1]`                          | 实体增删、召唤物、多人接入受数组位置约束 | 通过显式 ID 查找对象，数组只负责稳定遍历   |
| 所有怪物共享 `content.enemy`，枪械使用 `content.weapon` | 新增不同怪物、不同枪械时容易继续加分支  | 配置以 `cfg_id` 区分，实例各自保存状态 |
| `world.lua` 同时包含实体创建、伤害、死亡、终态判断和快照           | 新玩法持续集中到一个模块         | 逐步拆出构造、伤害、枪械、快照等职责       |

其中，枪械和怪物逻辑目前确实直接使用上述公共配置；这不是推测出来的架构问题，而是下一步支持多种内容时需要调整的具体入口。

**所以，这次基础类规划的重点不是“再增加几个类名”，而是把状态归属、行为入口、对象关系确定下来。**

## 二、推荐的总体关系

先从概念上这样组织：

```text
Entity：存在于当前游戏世界中的对象
│
├── Unit：具有角色运动与战斗能力的单位
│   ├── Player
│   └── Monster
│
├── LootEntity：地面掉落物
├── Projectile：有飞行过程的投射物，实际需要时再加
└── Interactable：箱子、机关、撤离点等交互对象
```

但是，实际实现不必构造复杂继承机制，而可以这样组合：

```text
Player
  = Entity 公共状态
  + Unit 公共能力
  + 玩家输入
  + 背包
  + 装备栏

Monster
  = Entity 公共状态
  + Unit 公共能力
  + AI 状态
  + 出生信息
  + 掉落规则引用

一件装备
  = Item 物品实例
  + 装备相关数据

一次技能释放
  = SkillCfg 配置
  + 释放者状态
  + CastState 本次释放过程
```

**“有组件”不等于必须立即实现完整 ECS。** 组件化本身也会增加组织复杂度；《Game Programming Patterns》的组件模式章节明确提醒了这一点。你现在更适合明确几个固定能力，而不是先开发组件注册器、动态查询语言和通用事件总线。([Game Programming Patterns][1])

## 三、`Entity`：只承担世界对象的最小公共身份

### 推荐职责

`Entity` 主要回答三个问题：

**它是谁？它在哪里？它是否仍然属于当前世界？**

建议的最小状态：

```text
Entity
    id                  当前对局中的实体 ID
    kind                player / monster / loot 等类型
    cfg_id              对应内容配置 ID
    pose                位置、朝向
    pending_remove      是否等待移出世界
```

碰撞体可以作为可选数据组合进去。生命值、弹药、背包、技能、AI 不建议直接进入 `Entity`。

例如，撤离点可以有位置和交互区域，但不需要血量；地面药品不需要枪械冷却。让它们继承一个已经包含完整角色状态的基类，只会产生大量无意义字段。

### 创建和销毁由谁负责

建议：

```text
Entity.new(...)          构造合法的公共状态
World.spawn(...)         分配身份，加入世界
World.find(id)           查找实体
World.remove(id)         在约定阶段移出世界
```

**不要让实体自行把自己从世界容器里删除。** 我建议先标记，再在 Tick 的固定阶段处理，以免遍历过程中改变集合。

还要区分：

```text
死亡 ≠ 立刻销毁实体
```

死亡后可能仍需要完成掉落、击杀归属、尸体表现和事件输出。当前代码就保留了死亡实体的位置和标识，这个边界值得保留。

### ID 的建议

至少在概念上区分：

| ID         | 含义          |
| ---------- | ----------- |
| `PlayerId` | 玩家身份        |
| `EntityId` | 某一局中的世界对象身份 |
| `CfgId`    | 内容类型        |
| `ItemId`   | 某一份具体物品的身份  |

对于可能延后处理的实体引用，建议使用：

```text
EntityRef = match_id + entity_id
```

当前每次开局都会重新创建实体，玩家实体使用 `"1"`。因此，只保存 `entity_id` 的旧操作，不足以区分“上一局的玩家”和“这一局的玩家”。

第一版可以规定**局内实体 ID 不复用**；将来确实引入对象槽位复用时，再增加代际编号，不必现在就把句柄系统做复杂。

## 四、`Unit`、`Player`、`Monster`：共用能力，不共用所有状态

### 1. `Unit`：玩家和怪物的公共部分

我建议增加一个 `Unit` 概念，也可以称为 `Creature`。对 Hunter 来说，`Unit` 更简洁。

```text
Unit
    entity              世界对象公共状态
    motion              速度、落地状态、运动限制
    health              当前生命值、最大生命值
    action              当前动作及动作约束
    faction             阵营
```

`skills`、`buffs`、`stats` 可以随需求补充，不必要求最初每个单位都拥有完整实现。

在 Luax 中，`Unit` 可以只是一个公共构造模块：先创建实体数据，再补齐角色能力。**它不一定是语言层面的基类。**

公共行为也不必全部写成 `Unit` 的方法：

```text
movement.step(...)      处理运动
damage.apply(...)       处理伤害
skill.try_cast(...)     处理技能释放
```

这样既能复用，又不容易把 `Unit` 养成一个巨大的“万能角色类”。

### 2. `Player`：局内玩家，不是整个账号系统

建议定义：

```text
Player
    unit
    player_id
    controls            已校验、等待模拟消费的输入
    bag                 局内背包
    equip               装备槽位
```

重点是把三种生命周期分开：

| 概念          | 生命周期        | 主要内容               |
| ----------- | ----------- | ------------------ |
| 会话          | 本次连接或本地服务实例 | 握手、请求关联、连接状态       |
| 局内 `Player` | 本次对局        | 位置、血量、输入、局内物品      |
| 持久化玩家数据     | 跨对局         | 已确认结算、解锁等实际需要保存的数据 |

**`Player` 不负责 TCP 收发，也不直接执行 SQLite 写入。**

第一版不必因此建立完整账号模块。可以继续保留本地玩家身份，只把“连接”“对局角色”“保存结果”三个概念分清楚。

另外，建议逐步用：

```text
world.player_entity_id
        ↓
World.find(...)
```

替代业务代码到处写 `world.entities[1]`。

当前只有一个玩家，也值得做这个改动，因为它首先解决的是“身份依赖数组位置”，并不是提前开发多人系统。

### 3. `Monster`：单位状态＋AI，而不是另一套战斗系统

建议定义：

```text
Monster
    unit
    spawn_id            来自哪个出生点
    ai                  行为状态、目标引用、行为计时
```

怪物配置则单独保存：

```text
MonsterCfg
    基础属性
    碰撞与运动参数
    感知参数
    可使用的攻击或技能
    AI 行为类型
    掉落表 ID
```

这里有一个重要区分：

> **怪物种类 ID、出生点 ID、怪物实例 ID，应该是三个不同概念。**

同一种怪物可以出生在多个位置；同一出生点可以先后产生多个实例。不要长期把这三个身份合并。

普通怪和 Boss，我建议先采用：

```text
Monster + 不同配置 + 不同行为模块
```

而不是不断增加：

```text
Monster
  → EliteMonster
    → BossMonster
      → RageBossMonster
        → PhaseTwoBossMonster
```

当前 AI 已有巡逻、追击、攻击状态，可以先保留这套结构；Boss 需要阶段变化时，在 AI 状态里增加阶段和相关计时即可。

**AI 负责决定“想做什么”，运动和战斗模块负责判定“能否做到、结果是什么”。** 玩家攻击和怪物攻击应尽量走同一套伤害处理，不各自维护扣血、死亡和事件逻辑。

## 五、`Skill`：至少区分配置、拥有状态和释放过程

`Skill` 最容易出现的问题，是把“技能说明”“角色冷却”“本次施法”全部装进同一个对象。

建议拆成三个概念：

| 类型           | 负责什么          | 示例字段                |
| ------------ | ------------- | ------------------- |
| `SkillCfg`   | 这个技能的规则       | 冷却、消耗、范围、目标规则、效果    |
| `SkillState` | 某个单位拥有该技能后的状态 | 技能 ID、等级、剩余冷却、次数    |
| `CastState`  | 当前正在进行的一次释放   | 释放者、目标、开始时间、阶段、是否中断 |

例如：

```text
SkillCfg
    “近战挥击需要前摇，命中范围内目标后造成伤害”

SkillState
    “这只怪物的近战挥击还在冷却”

CastState
    “这一次挥击已经开始，正处于前摇阶段”
```

不是所有技能都需要长期存在的 `CastState`。瞬时技能可以在一次处理过程中完成；只有存在前摇、持续、蓄力、延迟生效等过程时，再保存释放状态。

### 技能释放建议采用统一入口

概念流程：

```text
请求释放
    ↓
校验释放者状态、技能来源、冷却、资源和目标规则
    ↓
接受释放，按规则处理消耗与冷却
    ↓
进入释放过程，或立即执行效果
    ↓
效果交给伤害、治疗、Buff 等模块
```

需要明确约定：资源什么时候扣、冷却什么时候开始、打断是否返还、目标失效如何处理。不要让这些行为散落在各个技能脚本中。

### 对 Hunter 当前阶段，更应该先拆 `Weapon`

当前 `combat.lua` 实际承担的是射线枪械：扣弹、射击间隔、换弹、墙体遮挡和最近命中目标判定。

因此，我建议先实现：

```text
WeaponCfg
    弹匣容量、射击间隔、换弹时间、射程、伤害

WeaponState
    对应物品 ID、当前装弹量、射击冷却、换弹进度
```

备用弹药则根据设计放在背包或独立的弹药池中，避免以后多把枪共享弹药时各存一份。

这里的关系是：

```text
枪械物品提供射击能力
射击能力产生一次攻击
攻击通过统一伤害模块产生结果
```

**不必为了“技能统一”马上把一把枪包装成复杂技能框架。** 先让玩家枪械与怪物近战共享 `damage.apply()`，再逐步抽取公共释放规则，更符合你现在的进度。

另外，当前使用射线命中，不必每次射击都创建 `Bullet Entity`。等加入有飞行时间的火箭、箭矢、手雷，再增加 `Projectile`。

## 六、`Item`：物品数据，不等于世界实体

我建议先定义两个层次：

```text
ItemCfg：一种物品
    id
    kind
    max_stack
    关联的装备配置或使用效果

Item：一份具体物品
    id
    cfg_id
    count
    location
    必要的实例数据
```

例如：

```text
“基础步枪”是一个 ItemCfg

“这局拾取的那把基础步枪”是一个 Item
```

多个实例可以引用同一个配置，但实例之间的装弹量、耐久等状态可以不同。随机词条、强化等当前没有需求的字段，不建议先铺满。

### `Item` 和 `LootEntity` 应当分开

这两个东西解决的问题不同：

```text
Item
    这是什么物品？
    有多少？
    有哪些实例状态？

LootEntity
    它在地图哪里？
    能否被交互？
    对应哪个物品实例？
```

因此推荐：

```text
LootEntity
    entity
    item_id
    interaction_state
```

而不是：

```text
Item 继承 Entity
所有背包物品都带世界坐标和碰撞状态
```

### 物品位置必须有唯一事实来源

我建议在局内使用统一物品实例集合；背包、装备栏和掉落物通过 ID 引用实例。

必须保证：

> **同一个物品实例不能同时处于“地面”“背包槽位”“装备槽位”三个位置。**

可以把 `Item.location` 作为位置的权威记录，槽位表作为同步维护、可以校验或重建的索引，而不是再复制出几份完整物品数据。

拾取流程应先检查再修改：

```text
检查掉落物仍存在
    ↓
检查玩家状态、交互距离、背包容量
    ↓
在同一个逻辑处理阶段完成物品转移
    ↓
移除或更新地面掉落物
    ↓
输出结果
```

背包已满、重复请求或目标已被取走，都不能导致物品丢失或重复生成。

## 七、`Equip`：建议表示装备栏与装备操作，不再复制物品

“装备”这个词容易同时指三件事，建议在命名上分清：

| 概念              | 推荐表达                          |
| --------------- | ----------------------------- |
| 哪类物品可以装备、可以装在哪里 | `EquipCfg`，或 `ItemCfg` 中的装备配置 |
| 某一件具体装备         | 带装备数据的 `Item`                 |
| 玩家身上的装备槽位与操作    | `Equip` 模块及其状态                |

装备栏可以很简单：

```text
EquipState
    primary_weapon      ItemId
    secondary_weapon    ItemId
    armor               ItemId
```

**这里保存物品 ID，不再保存另一份完整物品。**

第一版只有一把枪，就先只有一个武器槽。不要为了未来可能存在的内容，一次定义十几个装备部位。

### 装备模块负责哪些规则

建议集中负责：槽位匹配、物品归属、换装条件、旧装备去向，以及换装对当前动作的影响。

比如换枪时需要明确：

```text
正在换弹，是否允许换枪？
换枪后旧枪的换弹是否取消？
正在执行的射击动作绑定的是哪把枪？
```

否则容易出现“拿 A 枪开始换弹，切成 B 枪后给 B 枪增加弹药”的状态串用。

### 属性如何处理

我的建议是：初期装备少时，在装备或 Buff 变化后直接重新计算最终属性。

```text
最终属性
    = 基础属性
    + 当前有效装备贡献
    + 当前有效 Buff 贡献
```

不建议在多个地方散落：

```text
穿上：攻击力 += 10
脱下：攻击力 -= 10
```

重算方案更容易检查“重复穿戴”“重复请求”“属性恢复”等情况。等实际性能数据证明需要优化，再做增量计算。

## 八、还需要哪些配套基础模块

你列出的类型之外，我认为下面几个模块比继续扩充继承树更重要：

| 模块           | 核心职责                  | 建议时机      |
| ------------ | --------------------- | --------- |
| `World`      | 持有局内状态、实体查找、生命周期和模拟组织 | 现在整理      |
| `Damage`     | 统一伤害、生死状态转换及结果输出      | 现在拆分      |
| `Bag`        | 容量、堆叠、物品转移和查询         | 接拾取时      |
| `Loot`       | 掉落生成与拾取规则             | 撤离闭环阶段    |
| `Extraction` | 撤离区域、条件、计时与中断         | 撤离闭环阶段    |
| `Settlement` | 生成结算数据、提交关联与重复请求处理    | 撤离闭环阶段    |
| `Buff`       | 持续效果、叠加、到期与来源         | 真正出现持续效果时 |

这里特别提醒两个 Hunter 相关的边界。

**第一，清怪或击杀 Boss，不等于完成撤离。** 当前切片会进入 `Cleared` 终态；完整撤离版本应把“目标达成”和“对局结束”分开，否则 Boss 死后直接冻结世界，后面的拾取与撤离就接不上。当前 `finish()` 确实会在清怪后终止战斗动作。

**第二，结算计算与存储成功不是同一件事。** 可以先生成结算请求并冻结待确认结果，但只有存储成功后才能确认奖励已经保存；失败和重试不能再次发奖。你的规划已经要求 SQLite 事务、结算去重和累计结果一起处理，后续应沿这个边界实现。

当前掉落和结算文件仍属于未进入正式模块清单的占位，不能把这些规划当成已有功能。

## 九、这些“类”在你的 Luax 项目中怎么落地

### 延续现有模块工厂，不把方法和状态混在一起

当前项目通过 `modules.json` 声明依赖，再由模块工厂返回函数表。建议继续使用这个方式。

例如，`entity.lua` 可以保持这种结构。下面只是接口结构示意，不是已经适配现有契约的替换代码：

```lua
-- 构造实体公共状态，不持有世界、网络或存储对象。
return function(deps)
    local api = {}

    -- 根据已校验的参数创建实体，身份由世界模块分配。
    function api.new(id, kind, cfg_id, x, y)
        return {
            id = id,
            kind = kind,
            cfg_id = cfg_id,
            pose = {
                x = x,
                y = y,
                facing = 1
            },
            pending_remove = false
        }
    end

    return api
end
```

随后：

```text
Unit.new(...)       调用 Entity.new(...)，补充角色公共状态
Player.new(...)     调用 Unit.new(...)，补充玩家状态
Monster.new(...)    调用 Unit.new(...)，补充怪物状态
```

对象状态中不保存网络对象、C++ 借用对象或每实例的行为闭包；行为函数保留在模块中，需要什么数据就显式传入。

这也更贴合现有 `export_state()`、`import_state()` 的纯数据导出与校验方式。

### 重构时，先保持现有模拟顺序

当前顺序是：

```text
玩家移动
    ↓
怪物移动
    ↓
玩家枪械处理
    ↓
仍然存活的怪物攻击
    ↓
裁定终态
```

这个顺序会影响同一 Tick 中谁能攻击、被玩家击杀的怪物是否还能出手。第一轮拆模块时，应保留它，不要把顺序变化混在“类结构重构”里。

### 内部状态不必等于网络结构

建议保留明确的转换边界：

```text
局内状态
    ├── 网络快照投影
    ├── 完整导出状态
    └── 持久化结算数据
```

这三种数据用途不同，不应要求它们结构完全一致。

例如，内部把弹药移动到 `weapon` 子状态后，仍可以暂时投影成现有协议的 `ammo` 字段。

但要注意，当前 `contract.json` 明确禁止额外状态字段，`world.lua` 也有严格的字段和实体校验。因此，**新增组件、改变状态结构，必须同步调整校验与状态版本；不是把字段换个位置就结束了。** 新增掉落物等网络对象时，再相应更新协议、桥接 schema 和客户端展示。

## 十、我建议你的实际实现顺序

不要一次建齐所有类型。按照能验证的成果分成四轮：

| 顺序                 | 主要改动                                                            | 验收目标                                  |
| ------------------ | --------------------------------------------------------------- | ------------------------------------- |
| **第一轮：拆现有战斗职责**    | 提取 `Entity / Unit / Player / Monster` 构造模块，以及 `Weapon / Damage` | 原来的移动、射击、换弹、死亡、清怪重开行为不变；导出导入仍正确       |
| **第二轮：摆脱单配置与数组身份** | 配置按 ID 查找；实体按 ID 访问；怪物保存独立出生引用                                  | 两种怪物可同时存在，各自使用正确属性和行为；增删实体不破坏身份关联     |
| **第三轮：接物品与装备**     | `Item / Bag / Equip / Loot`                                     | 可掉落、拾取、装备；背包满不会丢物品；重复操作不会复制物品         |
| **第四轮：完成撤离闭环**     | Boss 目标状态、`Extraction / Settlement`，按需要补 `Skill / Buff`         | 击杀 Boss 后仍可拾取撤离；保存失败不会假成功；重试与重启不会重复累计 |

你已有的开发约定是“先明确契约与不变量，再补测试和实现”，这四轮也适合分别形成小范围 intent，而不是写一份巨大的“通用对象框架”后一次落地。

**最终建议可以概括成一句话：先把现有的 `world / combat / ai` 拆清楚，再让 `Item / Bag / Equip / Loot` 接上撤离循环；基础类应当服务于这个游戏闭环，而不是让游戏反过来等待一套通用框架完成。**

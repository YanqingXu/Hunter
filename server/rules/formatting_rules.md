# R-FORMATTING：Hunter 排版规则

范围、等级和冲突处理见 [规则入口](README.md)。本文件管理布局；命名与函数职责见
[可读性规则](readability_rules.md)，表达式提取等语义变换见 [重构规则](refactoring_rules.md)。
默认只检查本次新增或修改的手工代码，生成代码与第三方源码不手工格式化。

## C++ 基本风格

适用于 `src/`、`platform/`、`tests/` 中手工维护的 C++ 文件；头文件与实现文件在各模块目录内并置。
新增代码使用 4 个空格缩进，函数和控制块左花括号另起一行，不用 Tab 对齐。
新建文本使用 UTF-8；修改现有文件保持其换行风格，避免无关编码或全文件换行差异。
字符串、原始字面量和预处理指令内的空白可能有语义，不能机械清理。

### R-FORMATTING-03-01 控制语句显式使用花括号

- **等级：MUST。** `if`、`else`、`for`、`while`、`do` 的执行体均使用花括号，单条语句也不省略。
- `else if` 可以直接连接下一个条件；分支不压在一行，空循环也应写清意图。
- 检查新增及修改的控制结构，不对未触达文件批量改写。

```cpp
if (!ready)
{
    return;
}
else if (paused)
{
    queue_input();
}
else
{
    process_input();
}
```

示例只说明排版，不定义输入调度逻辑。

### R-FORMATTING-03-02 相邻函数块之间保留一行空行

- **等级：SHOULD。** 两个相邻声明块或定义块之间保留一行空行。
- 每个具名函数声明前一行必须有中文职责注释；无独立声明时放在定义前，具体见 `R-READABILITY-02`。
  注释属于其后的函数块，空行放在注释之前，不放在注释与声明之间；工具指令必须紧贴声明时，
  按 `R-READABILITY-09` 保留位置，中文职责说明紧邻指令之前。
- 不在多行签名或注释内部机械插空行，也不在访问说明符与首个声明之间强行加空行。
- 命名空间、类型或条件编译隔开函数时，按相应结构分组。

### R-FORMATTING-03-03 手工代码不超过 100 列

- **等级：MUST（行宽）；SHOULD（表达方式）。** 手工 C++ 代码每行最多 100 列，
  包含缩进、空格和分号。为使检查可复现，本规则按 Unicode 码点计数，不按中文显示宽度计算。
- 能清楚地写在一行时保持单行；过长时按语义折行，续行多缩进一级。
- 有明确意义且不改变语义时，可先提取参数计算或转换结果；不为压成一行给简单参数制造别名。
- 声明、调用与条件均可折行。不得仅为行宽改函数签名、缩短清楚的名称、删除类型限定或增加包装层。
- 提取变量会改变短路、求值次数、生命周期或失败时机时，保留原逻辑并折行。
  这类提取属于语义变换，不能算作纯格式化。
- **例外：** 不可拆分且必须原样保留的字符串、路径或外部标识，可附简短理由超宽。
  注释中的完整 URL 也可保留。Markdown 表格、生成代码和第三方代码不适用代码行宽限制。
- 当前通过 diff 与编辑器检查，无已配置的自动阻断工具。

### R-FORMATTING-03-04 控制结构与相邻语句分组

- **等级：MUST。** 完整控制结构与前后语句之间各留一行空白；结构位于块首或块尾时，
  不在花括号内侧制造空行。
- `if/else if/else` 是一个整体，分支之间不插空行；`do` 与尾部 `while` 也保持连续。
- 函数体内默认不写步骤性注释；必要的局部原因说明按 `R-READABILITY-02` 紧邻相关代码放置，
  分组空行放在说明之前，不把说明与其解释的语句分开。调用契约仍放在声明前，整体实现原因可放在
  定义前；工具指令按 `R-READABILITY-09` 保留要求的位置。
- **例外：** 紧邻 `if` 的前一条语句仅在单行声明或初始化一个局部变量，且该变量直接参与
  条件判断时，两者之间不留空行。多行声明、多个变量或夹有其他语句不适用此例外。
- 宏与条件编译需要保持其语法和语义，不为排版破坏反斜杠续行或条件覆盖范围。

```cpp
const auto* cfg = find_cfg(cfg_id);
if (cfg == nullptr)
{
    return;
}

apply_cfg(*cfg);
```

### R-FORMATTING-03-06 纯格式修改保持行为与范围

- **等级：MUST。** 纯格式化只改变无语义的布局，不改变命名、签名、条件顺序、协议、schema、
  奖励计算、事务或异步调度。
- 同一任务包含逻辑与格式修改时，拆成可独立审阅的步骤或差异，并明确验证范围。
- 不顺手格式化未触达目录，不手改生成产物，不变更第三方风格。
- 用 diff 核对修改范围；涉及宏、字面量或预处理边界时额外核对语义，不能用“格式化”省略检查。

## Luax 脚本排版

`lua/` 中脚本使用 4 个空格缩进，以 `end` 对齐对应块，不套用 C++ 花括号规则。
函数之间和不同业务阶段之间保留一行空行，简单局部初始化与紧随判断可连续排列。
代码行宽、文本编码和纯格式修改边界沿用上述约定；语法、函数声明与模块装配以固定 Luax
候选的实际验证为准，不直接使用面向普通 Lua 的格式化器改写脚本。

Android 的 Java/Kotlin、构建脚本与其他工具语言遵循各自语言惯例和后续工程配置；
C++ 的花括号位置、控制结构空行规则不强制传播到这些文件。

## 验证

检查新增及修改行的缩进、块边界、行宽、空行和差异范围。纯文档调整只验证引用与示例；
实现代码按适用 intent 执行实际检查。引入格式化工具时须先核对其输出与本规则一致，
未被工具覆盖的要求仍由评审检查。

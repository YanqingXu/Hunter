# Hunter 服务端规则入口

本目录适用于 Hunter 服务端本次新增或实际修改的代码、脚本及相关设计契约。
当前已建立桌面框架、CMake 与契约测试；具体能力和已验证范围以 intent 与验证记录为准。
Unity 客户端、美术和策划目录不自动套用服务端的语言与排版规则。

## 阅读顺序与适用范围

1. 阅读 [服务端工作约定](../AGENTS.md) 和 [服务端规划](../plan.md)，确认任务范围。
2. 在 [intents](../intents/) 中建立或更新对应契约，明确不变量、线程、所有权、失败行为和验证入口。
3. 按下表读取适用规则；具体开发顺序遵循工作约定，不要求每次通读全部文档。

| 文档 | 用途 | 适用对象 |
| --- | --- | --- |
| [编码原则](coding_principles_rules.md) | 业务意图、模块边界、资源与失败保证的评审思路 | C++、Luax、平台适配与工具设计 |
| [排版规则](formatting_rules.md) | 花括号、缩进、空行、行宽和格式修改边界 | 手工维护的 C++；另有 Luax 排版小节 |
| [可读性规则](readability_rules.md) | 命名、中文注释、函数组织和控制流 | C++、Luax；中文注释约束覆盖所有自有代码 |
| [短类型命名规则](type_naming_rules.md) | `Types.h` 别名映射、统一使用和接口边界 | 所有服务端自有 C++，包括平台适配、测试与工具；第三方库除外 |
| [重构规则](refactoring_rules.md) | 行为保持、复杂度调查、小步变换和验证 | C++、Luax、相关平台适配与工具 |

短类型命名是全量约束，不限于本次触达的代码；统一定义来自
[src/common/Types.h](../src/common/Types.h)。已有等价短别名时必须使用，不能在各模块重复定义。

`R-READABILITY-01` 同样是全量约束：项目自有 C++ 与 Lua／Luax 的类、函数、文件、变量、
参数等所有命名必须简洁且可读，并统一使用 `Cfg`／`cfg` 等明确缩写。具体词表与契约边界见
[可读性规则](readability_rules.md)，不由各模块各自发明缩写。

中文注释同样是全量约束：所有自有代码文件开头说明职责与作用，所有具名函数声明前一行添加中文
说明，无独立声明时放在定义前；简单函数一句即可，必要调用约束必须说明。函数体内默认不写
步骤性注释，允许就近解释命名与结构无法充分表达的局部原因；匿名函数与回调按需说明约束。
禁止英文说明句，工具指令保留要求的原文与位置。信息分层、表达质量和位置例外见可读性规则的
`R-READABILITY-02`、`R-READABILITY-08`、`R-READABILITY-09`，不保留简单具名函数免注释的例外。

## 规则等级与冲突处理

- **MUST**：适用范围与触发条件满足时必须遵守；仅使用条款明确列出的例外。
- **SHOULD**：默认遵守；偏离时在代码、intent 或变更说明中留下简短理由。
- **REVIEW**：调查和评审信号，不因行数、参数数或嵌套深度直接判错或自动改写。
- 编码原则中的 `CC-*` 用于解释理由；各规范文件中的 `R-*` 用于定位具体规则。
  引用时写文件路径和编号即可，不要求额外生成流程报告。

任务要求和适用的 `AGENTS.md` 确定工作范围；`plan.md` 确定当前设计基线，已建立的
intent 细化具体契约。本目录的通用规则不能覆盖线程、协议、持久化、生命周期等业务契约。
若 intent 与规划不一致，应先明确并同步设计决策，再做依赖该决策的实现，不能挑选较宽松的
文档解释。格式偏好不能成为改变行为、所有权或接口的理由。

## Hunter 的设计基线

以下从 [plan.md](../plan.md) 摘要检查入口；细节及后续变更以规划与对应 intent 为准。

| 边界 | 实施时必须保持的约束 | 规划位置 |
| --- | --- | --- |
| 工具链与依赖 | C++23、Standalone Asio、CMake；Luax 从规划固定候选接入，实际标准库与 Android 支持待 P0 验证 | 第 1、5 节 |
| 模块与权威状态 | C++ 独占权威对象、生命周期和高频网络；Luax 决定玩法规则，只保留句柄和局部计算值 | 第 2、3 节 |
| 线程与所有权 | 逻辑线程独占 VM，禁止同步重入；存档线程独占 SQLite；跨线程任务拥有自身数据并携带关联信息 | 第 2、4 节 |
| 调度与容量 | 玩法命令在 Tick 边界处理；网络、存档不阻塞逻辑线程；队列有界；暂停不推进游戏时间 | 第 2、4 节 |
| 接口与数据源 | 仅回环 TCP + Protobuf；协议来自根目录 `protobuf/`，配置源表来自 `design/`，导表复用 `export/` | 第 1、3 节 |
| 脚本与宿主 | 不假定 Lua C ABI、传统 `require/package` 可用；普通 table 不直接跨 Host；schema、大小和数值精度显式定义 | 第 1、3、4 节 |
| 失败与结算 | 脚本输出经校验后提交；调用失败丢弃未提交输出并中止本局；结算事务去重，`Committed` 才是持久化成功 | 第 4、7 节 |
| 更新与发布 | 热更新仅供开发，在安全点切换；活动 Continuation 或未完成结算返回 `Busy`；发布关闭入口并使用离线签名 Bundle | 第 5、6 节 |
| 平台生命周期 | Android 同 APK 双进程为发布目标，Windows 为开发宿主；强杀后读取已提交存档，不隐式恢复未完成局 | 第 5、7 节 |

`lua/modules.json` 的正式清单、入口和桥接 schema 已随 SRV-004／005 落地；
未进入 active 契约的规划名称仍不能视为已存在的命令、接口或测试。

## 从外部规则迁入时的处理

- 保留四份文档的文件名与现有规则编号，便于对照；编号不表示继承原项目的工具或执行流程。
- 移除 GhostOL、GameModule、C++11／32 位专用限制，以及支付、跨服、GM 等首版范围外示例。
  示例改用 Hunter 的输入、配置、Tick、撤离与结算语义。
- 移除不存在的工程宪章、规则 YAML 索引、检查脚本、Gate、Agent 分工及报告字段依赖。
  本文是人工阅读入口，不引入额外索引系统。
- 保留显式花括号、100 列代码行宽、中文职责说明、最小修改和行为保持要求。
- 将按指标强制重构、跨行条件一律提取函数、判定函数一律拆成卫语句，改为按业务意图评审。
  换行本身不说明职责混杂；清楚的复合条件可以保留，避免只为排版制造函数。
- 函数排列保留由外到内的阅读方向，同时尊重 C++ 声明依赖与 Luax 局部作用域。

## 验证与维护

目前已有 intent 一致性检查与 Windows CI 配置，但没有通用编码规则检查器或格式化配置。
编码规则仍靠变更自检与评审执行，不能把契约测试通过等同于全部规则“工具通过”。
未来增加自动检查时，先固定工具版本与配置，并覆盖合法、非法和例外样例；
语义问题仍需契约与行为验证，不能靠正则或分数证明。

- 文档变更：检查相对链接、规则编号、交叉引用、示例一致性及与规划的冲突，不新增业务测试。
- 实现与重构：运行与风险相符的真实构建、契约或集成验证，记录实际命令、结果及未验证项。
- Android 行为：提供真机证据；Windows 通过不能替代真机生命周期、ABI、打包与资源释放验证。
- 新增规则：写清等级、范围、触发条件、要求、例外和验证方式，放入职责对应的现有文档。
  只有形成独立主题时才新增文件，并更新本入口；不要复制规划或 intent 形成第二份权威契约。

# Hunter 编码原则

适用于本次新增或实际修改的服务端 C++、Luax、平台适配与工具代码。
本文解释设计与评审的理由，`CC-*` 是分析坐标，不是独立的阻断规则。
范围、规则等级和设计基线见 [规则入口](README.md)，具体要求见
[可读性规则](readability_rules.md)、[排版规则](formatting_rules.md) 和
[重构规则](refactoring_rules.md)。

## 1. 业务意图与局部表达

**分析坐标：CC-01 业务意图、CC-02 命名、CC-06 调用点、CC-15 变量与表达式。**

- 名称表达正在检查的事实或执行的动作。明确区分输入接收、玩法裁决、结算请求和持久提交，
  不用一个 `success` 掩盖不同阶段。
- 所有自有命名都应简洁且可读，类、文件、函数、局部变量与参数统一使用明确缩写，
  如 `Config` 使用 `Cfg`／`cfg`；词表与强制要求见 `R-READABILITY-01`，不靠任意截断缩短名称。
- 单位、标识与状态容易混淆时直接表达，如 `tick_id`、`dt_seconds`、`operation_id`、
  `match_id`、`script_generation`。不同含义的 ID 不因底层类型相同就互相替代。
- 查询名称不隐藏修改、发包或存档；`can_extract` 与提交撤离结果承担不同职责。
- 业务调用点不应要求读者同时理解 Protobuf 字段解包、TCP 分帧、SQLite 事务和 Host 值转换。
  这些知识归属于各自边界。
- 变量靠近首次使用，保持单一角色。提取表达式先确认短路顺序、求值次数、数值范围和生命周期，
  不为了行宽提前执行有副作用的操作。
- 服务端自有 C++ 统一使用 `src/common/Types.h` 的短类型；映射和接入边界见
  [短类型命名规则](type_naming_rules.md)。短名不改变真实类型、所有权或协议表示。

例如检查去重插入结果时，具名结果比同时推导 `second` 与取反更容易理解：

```cpp
const bool inserted = seen_input_ids.insert(input_id).second;
if (!inserted)
{
    return;
}
```

这是局部表达示例，不定义正式输入去重算法或容器的线程安全契约。

## 2. 职责与控制流

**分析坐标：CC-03 函数职责、CC-04 正常路径、CC-09 阅读顺序。**

- 职责按变化原因与抽象层级判断，不按固定行数判断。顶层流程表达完整业务阶段，细节放在
  拥有相应知识的模块内。
- 卫语句可突出正常路径，但提前返回不能漏掉事务回滚、资源释放、状态恢复或完成通知。
- helper 应形成可命名职责、真实复用或测试边界。把一行调用再包一层不一定改善设计。
- 函数顺序帮助读者从入口理解子流程，同时满足语言的声明与作用域规则。
  不为满足视觉顺序改变 Luax 局部函数绑定或 C++ 初始化顺序。

## 3. 副作用、注释与失败保证

**分析坐标：CC-05 副作用、CC-07 注释。**

- 所有自有代码使用中文说明：文件说明职责与边界，类型说明状态归属与不变量，具名函数在声明前
  说明职责与调用契约，无独立声明时放在定义前；简单函数一句即可，不因名称清楚而豁免。
  字段与常量按需说明单位、范围及特殊值，共同约束集中维护。具体见 `R-READABILITY-02`、
  `R-READABILITY-08` 和 `R-READABILITY-09`。
- 函数体内默认不写步骤性注释，命名与结构无法充分表达的局部原因允许就近说明；整体实现原因可放在
  定义前，匿名函数与回调按需说明约束。工具指令保留要求的原文与位置，人工解释使用中文。
  注释须具体、准确并随行为更新；成功含义、失败后状态、线程、幂等与时序等调用约束归入声明前说明。
- 输出请求和输出实际执行是不同阶段。按规划，普通脚本调用的发包和存档先缓冲，入口成功且
  输出校验通过后才执行；失败后丢弃未提交输出并中止本局，不继续使用可能已部分更新的状态。
- `Accepted` 不等于 `Committed`。结算结果、去重键与累计存档在同一事务提交，界面不能提前
  把接收成功显示为保存成功。
- 失败上下文应能关联到服务实例、对局或操作，同时保持日志量有界。
  不以默认成功、静默重置存档或吞掉错误来“简化”失败路径。

## 4. 知识与复杂度

**分析坐标：CC-08 DRY、CC-13 KISS/YAGNI、CC-14 复杂度症状。**

- 去重的是需要同步变化的知识，而不只是相似语法。协议以根目录 `protobuf/` 为源，配置源表
  在 `design/`，导表在 `export/`；生成产物不得手工维护成第二来源。
- 世界状态与对象生命周期由 C++ World 唯一维护，Lua 使用句柄编写玩法规则；存储层负责
  事务而不决定奖励。不能为了方便测试在 Lua 再建立可独立修改的位置、生命或计时副本。
- 新抽象回应当前需求、平台差异、测试边界或风险隔离。首版不预付多房间、账号、跨服或
  分布式框架的复杂度；已有 Android 与 Windows 宿主差异是有效的适配理由。
- 检查三个问题：改一处是否牵动无关位置，理解局部是否需要记住过多信息，影响范围是否
  只能全局猜测。减少行数和增加设计模式都不能单独证明改善。
- 简单不表示删掉容量限制、超时、版本校验、事务去重和失败处理。

## 5. 接口与模块边界

**分析坐标：CC-11 信息隐藏与模块接口。**

- `src/` 承载共用 C++ 核心，`platform/` 承载宿主差异；`lua/main.lua` 组装入口，
  `lua/game/` 承载玩法，`lua/framework/` 放通用脚本支持。
- C++ 头文件与实现文件按模块放在同一目录，不另设 `include/`；接口边界通过职责和可见性表达，
  不通过头文件与实现文件分属两棵目录树表达。
- Host 接口表达受授权能力，脚本不直接接触 Socket、SQLite 连接、任意路径或裸 C++ 指针。
- Luax 的 `.lua` 后缀不意味着兼容普通 Lua。模块装配、可用语法和标准库都以规划固定候选
  的验证结果为准，不假定 `require/package` 或 Lua C ABI 存在。
- 跨 Host 的 schema、大小限制与数值表示必须显式约定；普通 table 留在脚本内部。
  不把 Protobuf 原生 JSON 映射直接当作脚本 schema，不通过浮点中转丢失 64 位 ID 精度。
- 返回引用、指针、视图或句柄前，说明所有者、有效期与失效条件；便利接口不能隐藏借用风险。

## 6. 资源与对象语义

**分析坐标：CC-12 资源所有权、CC-16 C++ 对象语义。**

- 先回答谁拥有、谁释放、在哪个线程、失败时怎样恢复，再选择 RAII、值类型或智能指针。
  共享指针不能替代明确的生命周期和取消设计。
- C++ 类型拥有资源时，检查复制、移动、析构和失败后的不变量。使用 C++23 能力前确认
  Windows 与固定 NDK 工具链可用，不把标准版本当作全部库功能已可用的证据。
- 逻辑线程独占 Runtime/Isolate，存档线程独占 SQLite 连接。跨线程传递拥有自身数据的
  任务与结果，不借用 VM 对象、临时字符串、栈变量或调用结束即失效的视图。
- 异步结果需要服务实例、操作 ID、必要的代次、deadline 与取消语义；失效句柄不能在新实例
  中复用。Host 回调需要再次执行脚本时延后调度，不同步重入。
- Tick 不等待存档或网络；队列有界，完成事件容量在启动工作前预留，不静默丢弃关键结果。

## 7. 安全修改与验证

**分析坐标：CC-10 最小验证边界、CC-17 行为保持型重构。**

- 重构只改变内部结构。修 Bug、改伤害、换错误码、改状态 schema 或提交时机都是行为变更，
  应在任务与证据中单独说明。
- 可观察行为包括返回结果、网络与存档、脚本入口、Host schema、随机数消耗、Tick 顺序、
  暂停与恢复、输出提交、取消及故障终态，不能只比较最终返回值。
- 先建立与风险匹配的行为基线，再小步重命名、提取、移动或封装；每步获得必要反馈。
  不借局部整理做无法说明收益的整模块重写。
- 测试断言公开行为、不变量与失败路径，避免锁死私有 helper 或容器形状。
  编译通过不能单独证明行为等价，Windows 通过不能证明 Android 生命周期正确。
- 规划和占位阶段只能验证文档、目录与引用。实现后记录真实执行结果，明确未验证范围。

## 8. 精简自检

- 业务步骤、单位、失败条件与副作用是否能直接读出？
- 复杂度是否放在真正拥有知识的模块，是否出现第二份权威状态或数据源？
- 线程、所有权、借用、句柄代次和释放路径是否清楚？
- 本次是结构整理还是行为变化，验证是否覆盖真正受影响的边界？
- 规则引用和验证入口是否真实存在，结论是否区分已规划、已实现与已验证？

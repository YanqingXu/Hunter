# R-READABILITY：Hunter 可读性与组织规则

适用于本次新增或实质修改的 C++ 与 Luax 代码，生成代码和第三方代码除外。
其中 `R-READABILITY-01` 是项目自有 C++ 与 Lua／Luax 代码的全量命名约束，不限于本次修改行；
项目维护的生成模板也须遵守，第三方生成产物保持生成契约，不手工改名。
`R-READABILITY-02`、`R-READABILITY-08`、`R-READABILITY-09` 是所有项目自有代码的全量
中文注释约束，包括 C++、Lua／Luax、平台适配、测试和工具；其他语言使用各自合法的注释语法。
等级与设计基线见 [规则入口](README.md)，纯布局见 [排版规则](formatting_rules.md)，
行为保持要求见 [重构规则](refactoring_rules.md)。示例名称用于说明意图，不定义正式接口。

### R-READABILITY-01 所有自有命名必须简洁且可读

- **等级：MUST。** 项目自有 C++ 与 Lua／Luax 的所有命名必须简洁，保留理解职责所需的信息，
  不使用冗长词组或重复上下文。不能仅为减少字符而造成歧义，也不能以可读性为由拒绝清楚的统一缩写。
- **范围：** 类、结构体、枚举及枚举值、类型别名、命名空间、模块、目录、文件、函数、方法、
  成员、局部变量、函数参数、常量、宏、模板参数，以及 Lua 自有 table 字段和导出项。
  核心、平台适配、脚本、测试和工具代码均适用，不能只规范公开接口而忽略局部命名。
- **缩写一致性：** 同一含义在 C++、Lua、文件名和调用点使用同一词根，大小写与连接方式沿用
  所属语言和模块风格。表示配置时统一使用 `Cfg`／`cfg`，不混用 `Config`、`Configuration`、
  `Conf` 等拼写。其他常用词按下表统一；仅替换完整语义词，不机械替换其他单词中的相同子串。

| 含义 | 统一词根 | 使用示例 |
| --- | --- | --- |
| Configuration / Config，配置 | Cfg / cfg | `MapCfg`、`load_cfg`、`cfg_id`、`Cfg.h`、`cfg.lua` |
| Context，上下文 | Ctx / ctx | `TickCtx`、`ctx` |
| Message，消息 | Msg / msg | `InputMsg`、`send_msg` |
| Request，请求 | Req / req | `SaveReq`、`req_id` |
| Response，响应 | Rsp / rsp | `SaveRsp`、`rsp` |
| Position，位置 | Pos / pos | `spawn_pos`、`set_pos` |
| Direction，方向 | Dir / dir | `move_dir` |
| Identifier，标识 | Id / id | `match_id`、`item_id` |

- 表中缩写只在对应含义下适用；例如 `Dir` 若同时可能表示目录与方向，就增加必要限定或保留
  明确词汇。表外名称优先选常用短词，不自创只有作者知道的截断词或首字母串。
  已经简洁清楚的 `world`、`loot`、`tick` 等保留，不要求每个词都缩写。
- **局部与跨边界：** 很小作用域可使用 `i`、`x`、`y` 等常见索引或坐标名；跨函数、模块或
  较长作用域时保留角色信息。避免 `a`、`b`、`c1`、`cfg2` 这类无法区分业务角色的名称。
  已有清楚上下文时用 `cfg`，同时存在地图和武器配置时用 `map_cfg`、`weapon_cfg`。
- **语义保留：** 保留必要的动作、状态、单位和 ID 归属，例如 `load_cfg`、`can_extract`、
  `dt_seconds`、`payload_bytes`、`tick_id`。查询不隐藏发包、存档或状态修改；
  `committed`、`generation`、`idempotency_key` 等没有清楚替代名时保留准确术语。
- **文件与类型：** 文件名反映主要类型或模块，相关声明与实现使用同一主体名，例如
  `MapCfg.h` 与 `MapCfg.cpp`；Lua 文件和模块名使用一致词根，不堆叠无意义的前后缀。
  `Types.h` 已定义的短类型直接遵循 [短类型命名规则](type_naming_rules.md)，不另造缩写。
- **契约边界：** 第三方库、标准入口、override、JNI 或第三方生成接口要求的名称保留契约。
  已冻结的协议字段、存档键、Host namespace、脚本入口和模块清单不能孤立重命名；项目自有
  名称变更需同步调用方与映射并验证兼容性。规划中的逻辑名称不等于全部已经冻结。
- **验证：** 检查本次涉及的所有命名类别及跨语言词根是否一致，读者能否在声明和使用处直接
  理解含义；已有代码改名按 `R-REFACTOR-02` 搜索代码、字符串引用、构建列表、模块依赖和文档。
  命名要求覆盖全量代码，但本次规则维护不自动扩展为无关文件的批量重命名。

### R-READABILITY-02 所有函数声明前一行必须有中文注释

- **等级：MUST。** 所有自有函数、方法的声明前一行必须有中文职责注释，注释与声明之间
  不留空行。包括构造、析构、运算符、简单访问器、谓词、适配函数、override、测试与工具函数，
  不因函数短小或名称清楚而豁免。
- 有独立声明的 C++ 函数在声明前说明调用契约；实现处无需重复相同说明，整体实现原因可写在
  定义前。没有独立声明的函数、头文件内直接定义的函数以及 Lua 函数，在定义前一行添加中文注释。
- 模板、属性或装饰器属于声明整体，注释紧贴该整体的第一行，不插入多行签名内部。
  需要多行说明时，中文注释块的末行紧邻声明；工具指令的位置例外见 `R-READABILITY-09`。
- **职责与约束：** 用一句话概括职责；简单函数一句即可，不强制凑长度或套用完整模板。
  存在影响正确调用的参数单位、线程、所有权或副作用约束时必须说明；还应明确适用的成功含义
  （已受理或已完成）、失败后状态是否改变、是否允许重复调用，以及回调时机、线程和同步触发可能性。
  仅补充实际存在的约束，不逐项翻译签名，也不用“处理数据”“执行逻辑”等空泛描述代替职责。
- **局部原因：** 函数体内默认不写步骤性注释，实现步骤通过简洁命名和清晰结构表达。
  命名与结构无法充分表达的执行顺序、兼容绕行或数值处理原因，允许紧邻相关代码写中文说明，
  不逐行翻译实现，也不靠注释弥补可消除的命名歧义。
- 函数体内的具名局部函数在定义前说明职责；匿名函数（含 lambda）和回调按需就近说明捕获对象
  生命周期、执行线程等必要约束，不强制为每个匿名函数添加职责注释。其内部同样遵守局部原因规则。
- C++ 使用 `//` 或中文文档注释，Lua／Luax 使用 `--`；内容语言按 `R-READABILITY-09`。
  行为变化时同步更新职责、约束和实现原因，不能保留已经失效的说明。
- **验证：** 逐项检查声明或无独立声明的定义前说明，确认调用契约准确、局部注释必要且位置恰当；
  不以“简单函数”“已有基类说明”或“名称已经清楚”为由跳过具名函数的职责说明。

以下示例只说明注释写法，不定义正式接口或业务契约：

```cpp
// 返回当前待处理请求数。
usize pending_count() const;

// 将结算请求加入存档队列；返回成功仅表示入队，持久化结果另行通知。
// 队列已满时返回失败，不提交请求。
bool enqueue_settlement(const SaveReq& req);
```

局部原因示例：“先复制消息内容，因为归还缓冲区后原视图失效。”适合紧邻复制操作；
“复制消息”只是复述步骤，不必添加。示例未列出的线程、所有权与通知约束按实际契约补充。

### R-READABILITY-03 函数按职责组织并尊重语言依赖

- **等级：SHOULD。** 同一类或模块优先按“生命周期／公开入口 → 核心流程 → 子流程 → helper”
  组织，头文件声明与实现的主要顺序保持一致。
- **例外：** C++ 文件内 helper、模板或类型需先声明时可置前；Luax 局部函数按作用域和依赖
  顺序定义。不能仅为入口置顶改变绑定关系、初始化顺序或引入大量无意义前置声明。
- 只服务单个模块的 helper 保持最窄可见范围，不因为提取函数就放入公共头文件或通用框架。
- **验证：** 按调用方向检查阅读路径，并确认重排未改变声明、名称查找和初始化语义。

### R-READABILITY-04 深嵌套触发职责评审

- **等级：REVIEW。** 控制流达到三层及以上，或正常路径难以看清时，检查是否混合职责。
- 优先考虑安全的提前返回或提取完整子流程；天然层级数据、固定有界遍历或强顺序流程可保留。
- 不为减少缩进复制数据、增加缓存、改变遍历顺序或共享状态。保留更深嵌套时说明业务原因。
- **验证：** 核对早退、失败时机、随机数消耗、资源释放及副作用顺序；具体手法见 `R-REFACTOR-13`。

### R-READABILITY-05 条件表达领域事实，副作用清楚可见

- **等级：MUST（触发时）。** 条件混合修改、结果解包、多重取反或不同层级判断，导致业务含义
  难以读出时，应在保持语义的前提下先执行操作并命名结果，或提取合适的只读谓词。
- 简单空值、范围、枚举检查可直接保留。清楚的复合条件可以折行，换行不强制触发函数提取。
- 拆分会改变短路、调用次数、临时对象生命周期或失败时机时，保留原实现并说明约束。
  不能为了形式合规提前执行被短路保护的查询或修改。
- **验证：** 检查真实求值路径与副作用，不用正则禁止所有函数调用或成员访问。

```cpp
const bool inserted = seen_input_ids.insert(input_id).second;
if (!inserted)
{
    return;
}
```

这只表示一次插入及其判断，不意味着所有重复请求都应无响应地返回。

### R-READABILITY-06 封装需要真实职责

- **等级：REVIEW。** 仅透传一次调用、没有增加领域语义、校验、转换、错误处理或稳定边界的
  wrapper 应考虑内联，不因函数只有一行就直接判错。
- Host 适配、平台差异、能力约束、测试替身和兼容接口可能需要很薄的封装，保留时指出其职责。
- 复杂条件形成独立业务概念时可以提取谓词；普通状态检查不必层层包装。
- **验证：** 检查封装是否减少调用方需要知道的信息，是否只是增加跳转阅读。

### R-READABILITY-07 长签名保持接口自说明性

- **等级：SHOULD。** 先按 `R-READABILITY-01` 使用简洁名称与统一缩写，签名仍过长时按语义
  折行，不仅为 100 列限制删除必要的角色信息或引入无意义别名。
- 多个参数类型相同或角色容易混淆时保留有意义的参数名；定义中的具名参数表达实际用途。
- 类型别名应形成稳定领域词汇并位于最窄有效范围，不创建 `R`、`P`、`Ctx1` 等模糊缩写。
- 项目统一短类型遵循 [短类型命名规则](type_naming_rules.md)，`Str`、`Vec`、`i32` 等不属于
  无意义缩写；其声明集中在 `src/common/Types.h`，所有自有 C++ 代码统一使用。
- 不为减少参数数或行数改变 `const`、引用、指针、值传递方式、参数顺序、所有权或错误语义。
- Luax 入口与 Host 参数名称、顺序和类型受契约约束，也不能只为排版改变。
- **验证：** 对照完整接口与调用方，区分名称布局变化和实际契约变化。

### R-READABILITY-08 自有代码文件开头说明职责与作用

- **等级：MUST。** 所有自有代码文件必须有中文职责说明，不能整个文件没有中文注释。
  C++ 头文件开头必须用一至三行中文说明该文件的职责、作用和必要的公开边界，位于首个
  `#pragma once`、include guard 或其他代码之前；实现文件、Lua 模块和工具代码同样在开头说明职责。
- 语言要求的首行指令和必须保留的许可声明保持合法位置，中文职责说明紧随其后。
  没有注释语法的数据文件不硬塞注释，说明写在对应契约或说明文档中。
- 说明应概括真实职责、状态归属或使用边界，不逐项罗列符号，也不只写“公共定义”“模块头文件”。
- **信息分层：** 文件说明模块职责与边界；类型说明状态归属和不变量；函数说明调用契约；
  字段与常量按需说明单位、有效范围和特殊值。说明靠近所属对象，局部对象的说明遵守
  `R-READABILITY-02` 的局部原因规则，不为补注释扩大作用域或移动声明。
- 共同约束在所属层级集中维护，必要时引用已有类型说明或 intent，函数只补充自身职责和差异；
  不把同一约束复制到每个函数，也不以引用代替函数自身的中文职责说明。
- 占位代码继续明确“当前无实现”；实现落地后再更新说明，不能用注释宣告功能完成。
- **验证：** 全量要求不受文件是否新增或本次是否触达限制；核对文件说明的位置、中文内容及
  与实际职责的一致性。第三方与生成边界按 `R-READABILITY-09` 处理。

### R-READABILITY-09 所有自有代码注释使用中文

- **等级：MUST。** 自有代码的文件说明、函数说明、类型与成员说明、待办和预处理结尾说明等
  全部用中文表达，不写英文说明句，也不保留仅含英文单词或标识符的尾注。
- 中文句子可引用准确的代码标识符、类型、接口名、单位或 URL，例如“通过 `Tick` 推进游戏时间”；
  保留技术名称不等于允许英文说明句。不能只加“说明”两个字后继续写英文正文。
- **表达质量：** 使用直接、具体的中文，同一领域概念使用一致术语；少写“该函数用于”等套话。
  不用“优化性能”“确保安全”等缺少具体条件或机制的结论代替说明。
  `TODO` 等待办标记后的正文使用中文，写清缺失内容和完成条件，不能只写“后续完善”。
- **工具指令例外：** `NOLINT`、`clang-format off` 等供工具识别的注释保留工具要求的原文、
  参数和位置，允许出现在函数体内；人工解释理由使用中文，不把普通英文说明伪装成工具指令。
  若工具要求指令紧贴声明，中文职责说明紧邻放在指令之前，中间不留空行；需要成对的指令保持配对。
- 注释按 `R-READABILITY-08` 分层，声明前说明与局部原因按 `R-READABILITY-02` 放置；
  不能靠删除信息隐藏重要约束，也不为满足中文要求添加无意义文字。
- 项目维护的生成模板遵守相同要求，从源模板修改，不手工修改生成产物。
  第三方库、第三方生成器控制的代码及必须原样保留的许可文本保持原样，不翻译或删改。
- **验证：** 检查注释位置、语言、准确性和必要性，以及行为变化后是否同步更新；区分工具指令
  与人工说明。字符串、日志文本及源码标识符不是注释，不能用“发现英文字母”代替注释语义检查。
  当前通过人工检查与搜索执行，没有自动注释检查器。

待办示例：“TODO：补齐队列满时的失败通知；覆盖拒绝入队且不重复通知的测试后移除此待办。”
此示例只说明缺失内容和完成条件的写法，不新增业务任务。

## 评审收口

以上规则目前由自检与评审执行，没有标识符黑名单、函数计数器或注释检查器。
优先检查本次修改的命名、职责、状态与副作用，再核对语义变换的验证证据。
注释评审关注信息是否准确、必要、位置恰当，以及是否随行为变化同步更新，不以篇幅或数量代替质量。
发现问题时引用本文件及具体 `R-READABILITY-*` 编号，不把调查信号当作自动重写授权。

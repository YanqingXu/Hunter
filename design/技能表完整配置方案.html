01

三张表怎样分工

工作表 保存内容 与其他表的关系
技能|Skill 技能 ID、名称、技能点成本、作用对象、生命周期、启用状态和展示资源 一项技能对应一条 Skill 记录和一至八条效果记录
属性|Attribute 稳定属性代码、名称、作用对象、单位、可用运算和参数语义 一个属性可被多个技能引用，属性代码只在这里维护
技能效果|SkillEffect 哪个技能修改哪个属性、使用什么运算、参数是多少 SkillIdx 引用技能表，AttributeId 引用属性表

例如“灵缇”由技能表定义名称及成本，属性表定义 run_speed 的单位是毫米/Tick，效果表配置 mul_bp=12000。奔跑速度基础值仍来自角色表 Run，无需在技能表重复填写。

基础属性仍归属角色、武器、工具等原始配置。动作触发位置、适用道具筛选和技术边界由对应属性处理器实现，属性表中的代码不能作为脚本执行。

02

与现有字段相比如何调整

表 现有字段 推荐调整 原因
Skill SkillIdx、Name、Desc、Cost 保留 保持原技能 ID、名称和成本，方便旧引用迁移
Skill SkillType 删除 当前没有明确执行语义，容易与类别、生命周期混淆
Skill SkillAttribute 删除 技能的属性关联统一放到效果表，一项技能可有多条效果
Skill EffectDesc 保留为客户端展示字段 展示实际效果，不参与运行计算
Skill Target、Category、Lifetime 保留并固定枚举 明确作用对象、数值/机制类别和消费时机
Skill IconId、AnimId、EffectId、SoundId 保留为客户端资源字段 资源尚未交付时可以留空
Skill 无 新增 Enabled，int32，只允许 0/1 允许完整保留未实现技能，避免误加入可选择内容
Attribute AttributeId、Name 保留，原 1～10 ID 不变 保持属性身份稳定
Attribute AttributeType 删除，新增 Target 用 player/weapon/tool 代替含义不清的数字分类
Attribute 无 新增 Stat、Unit、AllowedOps、ValueMode 建立可校验的属性字典
SkillEffect EffectIdx、SkillIdx、Op、Value 保留 继续采用一行一个效果和整数运算
SkillEffect Stat 改为 AttributeId，类型改为 int32 通过属性外键避免属性代码拼写错误及重复维护

推荐目标结构中，效果表只填 AttributeId，不同时保留一个可编辑的 Stat。解析时从属性表查出 Stat，仍投影为现有运行结构 {stat, op, value}。

本次不增加技能等级、技能依赖、冷却公式或复杂条件表达式。一个技能 ID 本局最多持有一次，常驻属性不需要各自填写动作冷却。

01 SkillIdx技能 ID int32 server/client/key

给一项技能提供稳定身份，连接效果记录、技能物品、配装和局内持有列表。

字段职责
给一项技能提供稳定身份，连接效果记录、技能物品、配装和局内持有列表。
为什么需要这个字段
技能名称会随文案调整，Excel 行位置也会因排序改变，二者都不能承担身份。现有 skill.lua 的 supported 按技能 ID 判断支持范围，cfg_build.lua 又把 ID 转成字符串作为 content.skills 的键；因此继续沿用 1～15，才能保住旧物品引用、配装记录和技能消费记录之间的对应关系。更改 ID 是身份迁移，不应作为整理表格的操作。
为什么使用这个类型
int32 与现有主键导出和外键读取一致；正整数可稳定比较和排序，不引入名称大小写、前导零或字符串别名。表中填写数字 5，运行模型可以转为键 "5"，两者是同一身份。
为什么这样导出
server 用它识别配置和核验持有技能；client 用它绑定技能卡、选择项和权威状态。key 标记告诉导表工具这是唯一主键；三者必须同时存在，不能只给客户端一个显示序号。
合法值与填写规则
必填、全表唯一、1～2147483647 的整数；本版保留 1～15。不能用 0 表示空技能，不能填公式或重复已有 ID；删除记录前需检查全部 SkillEffect、物品及默认配装引用。
正确填写示例
灵缇填写 5；其效果 501 的 SkillIdx 也填写 5。
常见错误与后果
把技能按名称排序后重编号，会让旧 ID=5 的配装指向其他技能；把 EffectIdx=501 当成技能 ID，会查不到 content.skills["501"]。
与其他字段的分工及取舍
SkillIdx 只管身份，不表达类别、等级或效果顺序；这些分别由 Category、未来独立等级结构及效果关系承担。新增技能继续分配新 ID，避免为了连续编号复用已废弃 ID。
02 Name技能名称 string server/client

提供策划、调试和技能界面共同使用的可读名称。

字段职责
提供策划、调试和技能界面共同使用的可读名称。
为什么需要这个字段
服务端已有技能配置校验要求 name 是非空字符串，说明名称不仅是美术资源旁的一行字，也承担配置排错时的可读性。例如看到技能 10 的名称稳定瞄准，评审能直接联系其原策划条目，再结合效果确认它实际修改的是射击间隔。保留名称但不拿名称匹配效果，可以让后续改名不影响玩家已有技能和运行计算。
为什么使用这个类型
string 能保留中文名称，不用数值枚举限制命名；当前工具只支持 int32/string，直接保存文本最清楚。名字不是 ID，不应改为与 SkillIdx 重复的一列数字。
为什么这样导出
server 保留名称以满足现有共享技能模型的 name 字段和校验；client 显示技能卡及持有列表。双方名称一致便于联调定位，但运行身份仍以 SkillIdx 为准。
合法值与填写规则
必填非空 string；建议去掉前后空格和换行。本版采用现有 15 项名称；可以改名但必须保留 SkillIdx，不以重名来判断两个技能是否相同。
正确填写示例
SkillIdx=5 的 Name 填写灵缇。
常见错误与后果
只填 IconId 后把 Name 留空，会违反现有 name 非空门禁；把 Name 填成 run_speed，会把玩家名称与处理器代码混在一起。
与其他字段的分工及取舍
Name 描述这是什么技能；Desc 解释设计意图，EffectDesc 解释具体效果，Stat 指向执行规则。未来做多语言可增加文本键或本地化表，不能用翻译后的名称替代稳定 ID。
03 Desc技能说明 string client

保留技能的设计意图和原始概念，便于技能卡与策划评审理解。

字段职责
保留技能的设计意图和原始概念，便于技能卡与策划评审理解。
为什么需要这个字段
原描述如提升一定奔跑速度、非消耗品道具额外增加携带量，能够表达方向，却不能唯一决定倍率、工具筛选或状态变化。单独保留 Desc，可以追溯最初意图，同时把本版具体约定写在 EffectDesc 和数值表中；尤其货运骡子已经澄清为每种工具的携带次数，后续不会再因为一句概念说明而误实现成增加背包格。
为什么使用这个类型
string 适合自然语言，可以包含必要的中文标点；采用 int32 无法保存完整语义。该文本不会被拆词执行，所以不需要塞入公式或代码。
为什么这样导出
仅 client：用于技能介绍或说明面板。server 的 cfg_build.lua 当前不读取 Desc，技能实际效果取自 effects；不让说明参与服务器计算，可以避免改文案影响技能数值。
合法值与填写规则
允许空字符串，但完整配置建议填写简短、明确的设计描述；不能以文本中出现的百分比代替效果行，不得声称尚未实现的规则已经运行。
正确填写示例
精力充沛填写降低奔跑时体力消耗；实际建议倍率另在效果 301 中填写 7000。
常见错误与后果
只把 Desc 改为奔跑消耗降低 30%，却不增加或调整 SkillEffect，服务端不会从这句话解析出 7000。
与其他字段的分工及取舍
Desc 相对稳定，EffectDesc 随参数变动；两列允许内容接近，但目的不同。未来可接本地化文本管理，本版不引入脚本表达式或条件 DSL。
04 Cost消耗技能点 int32 server/client

规定选择该技能时占用多少角色技能点。

字段职责
规定选择该技能时占用多少角色技能点。
为什么需要这个字段
现有 skill.check 会累加所选技能 cost，并在非已有持有校验时与角色 skill_points 比较；因此成本是配装合法性的一部分，不能仅在界面上显示。将成本集中在 Skill 中，让死灵法师的两条效果仍只收取一次技能点，也能避免未来复合技能因为效果条数增加而意外变贵。本版沿用所有技能成本 1，不把建议效果强弱直接推导为新价格。
为什么使用这个类型
int32 与现有整点预算相匹配，避免 0.5 点等需要新计量契约的数值。零是合法免费成本，必须显式写 0，空值不能当作免费。
为什么这样导出
server 校验技能点预算，client 显示成本并计算选择预览；客户端预算用于交互提示，最终选择仍受服务端校验。
合法值与填写规则
必填整数，0～10000；本版 15 行均为 1。不能写 1点、百分号、公式或负值；免费技能写 0 并确认其发放渠道。
正确填写示例
军需官 Cost=1；选择两个成本均为 1 的技能，合计占用 2 点。
常见错误与后果
把 Cost 放在两条复活效果上，会造成重复计费；留空并期待导出补成 0，会把配置缺失掩盖成免费技能。
与其他字段的分工及取舍
Cost 是技能点成本，不是货币价格、道具数量或局内次数；Lifetime 控制成功触发后的消费，物品和永久资产交易仍由其各自配置负责。未来分等级成本应跟随等级记录扩展。
05 Target作用对象 string server/client

声明技能修改猎人、已配装枪械，还是符合条件的工具。

字段职责
声明技能修改猎人、已配装枪械，还是符合条件的工具。
为什么需要这个字段
三个对象的基础值和应用位置不同：奔跑速度来自 Player.Run，枪械初始备弹来自 Weapon.InitialReserve，医疗包治疗量来自 Tool.Value。显式 Target 能在构建时阻止把医疗包效果错误挂到 weapon 技能，也能帮助客户端解释作用范围。开箱大师应归 player，因为它改变猎人在箱子交互中的奖励能力，箱子本身不是当前三类目标中的一种。
为什么使用这个类型
string 用 player/weapon/tool 三个可读枚举，避免原数字分类需要猜含义；大小写固定可直接与 Attribute.Target 比较，不依赖展示名称或任意对象路径。
为什么这样导出
server 当前读取 target 并检查三类合法值；目标与属性一致的更完整校验仍需在迁移中补齐。client 可按对象说明能力范围，但不能据此自行发放效果。
合法值与填写规则
必填且严格为 player、weapon、tool 之一；每条引用属性的 Target 必须一致。复活两项和开箱大师为 player，货运骡子为 tool。
正确填写示例
枪斗术 Target=weapon，引用 AttributeId=5；灵丹妙药 Target=tool，引用 AttributeId=9。
常见错误与后果
把开箱大师填成 tool，会错误暗示它只增强某个配装工具；把 skill 的 tool 与属性的 weapon 混用，会形成跨对象不一致配置。
与其他字段的分工及取舍
Target 定义对象大类，具体 medkit/bomb/非消耗品工具筛选由登记处理器决定；本版不增加自由填写的过滤条件。未来新增怪物或队伍目标时，应同步新增处理器及校验枚举。
06 Category效果类别 string server/client

区分基础数值修改与改变行为结果的机制技能。

字段职责
区分基础数值修改与改变行为结果的机制技能。
为什么需要这个字段
同样使用整数参数，负重 add=1 是修改装备上限，满血复活 add=1 却是开启结果覆盖规则，二者不能仅凭 Value 的大小区分。Category 让技能层明确 numeric 或 mechanic，方便构建门禁和界面分类；现有复活校验也要求 mechanic。开箱大师的额外道具数量虽然是数字，它仍需要成功交互和奖励原子提交，所以归机制类更符合实际执行。
为什么使用这个类型
string 保存 numeric/mechanic 的语义枚举，比未经说明的 1/2 更易评审；这不是代码类名，不允许填任意新字符串绕过处理器能力校验。
为什么这样导出
server 当前读取 category，并在复活成对效果中要求 mechanic；client 可使用同一类别展示。类别本身不会让未实现的奖励箱或容量规则自动生效。
合法值与填写规则
必填 numeric 或 mechanic；技能 1、2、14 为 mechanic，其余为 numeric。新效果需要按已登记机制契约确定类别，而不能只看 add 或 mul_bp。
正确填写示例
死灵法师 Category=mechanic，虽然 revive_hp 的 Value=25；灵缇 Category=numeric。
常见错误与后果
把复活写为 numeric 会违背现有 revive 的类别门禁；将开箱写 numeric 并期待复用属性乘法就生成道具，会缺失交互提交规则。
与其他字段的分工及取舍
Category 表达技能层行为类别；ValueMode 表达单条属性参数语义，Lifetime 表达消费时机。mechanic 可以常驻，不能把它等同于 once；未来复杂技能可有额外标签，但不应挤进本列。
07 Lifetime生命周期 string server/client

声明技能在本局内持续生效或成功触发后消费的规则。

字段职责
声明技能在本局内持续生效或成功触发后消费的规则。
为什么需要这个字段
复活资格必须成功提交后才消费，否则玩家在体型放置失败或重复死亡请求中会无故丢失技能。现有 kind 字段接收 passive/once/death，本版保持其行为：死灵法师成功复活后消费，重振旗鼓也在成功复活提交时移除；death 不能照字面提前解释成死亡瞬间删除。明确这列可让配置、原生玩家状态和客户端消费表现使用同一时机。
为什么使用这个类型
string 使用现有三种可读枚举并投影到 kind，不需额外布尔组合。三个枚举是既有契约，不能填次数 1 或秒数来替代。
为什么这样导出
server 依据 kind 和原生玩家提交状态处理有效技能及消费；client 用同一生命周期提示本局使用限制，并等待权威消费结果。跨局永久资产的保留结算另有契约。
合法值与填写规则
必填 passive、once、death；技能 1 用 once，技能 2 用 death，其他用 passive。death 按本版现有语义在成功复活提交时消费，失败或死亡瞬间不提前删。
正确填写示例
死灵法师 Lifetime=once；重振旗鼓 Lifetime=death；开箱大师 Lifetime=passive，允许每个适用箱子各成功触发一次。
常见错误与后果
死亡回调刚发生便移除 death 技能，会让重振旗鼓无法参加复活计算；把开箱大师填 once，会误变为整局仅额外奖励一次。
与其他字段的分工及取舍
Lifetime 管本局技能有效性，箱子一次性使用状态属于箱子，工具次数属于工具数量；它不表示动画长度、冷却时间或永久库存消费。未来新增限次技能应明确定义新契约。
08 EffectDesc效果展示说明 string client

向玩家解释当前参数对应的收益、范围和限制。

字段职责
向玩家解释当前参数对应的收益、范围和限制。
为什么需要这个字段
本版有多个容易误读的效果：稳定瞄准修改射击间隔而非瞄准精度，弹药大师只增加初始备弹而不扩弹匣，猫步减少行动声传播半径而非必然隐身。EffectDesc 应写出当前精确百分比和这些边界，减少玩家根据名称产生的误判。它与效果参数共同维护，既能直接支撑界面，也能让评审快速发现数值改了而说明没有改的配置差异。

为什么这样导出

正确填写示例

Value=8000 却写射击速度增加 20%，会把间隔减少 20% 和频率增加 25% 混淆；货运写自动获得 1 次，会误导实际容量规则。
与其他字段的分工及取舍
EffectDesc 是参数的阅读解释，Desc 保存概念意图；实际能力由属性处理器决定。未来可用模板辅助生成比例文案，但仍须保留机制边界及人工审阅。

属性 Target 固定能力归属，技能 Target 是整体声明；两处重复是为了可校验关系，而非两套可独立修改的含义。未来跨对象技能应先扩契约，不允许悄悄放宽一致性。
05 Unit参数单位 string server/client

固定基础值与加法参数的计量单位，避免时间和距离换算误配。

字段职责
固定基础值与加法参数的计量单位，避免时间和距离换算误配。
为什么需要这个字段
项目采用整数 Tick 和毫米，奔跑速度是毫米/Tick，医疗时间是 Tick，投掷距离是毫米；不写单位时，填写 2 很可能被误认为 2 秒而实际只持续 2 Tick。Unit 也说明 add 的固定增量怎样解释，同时必须说明 mul_bp 是无量纲万分比因子，不随 hp、mm、tick 改含义。单位集中维护能使效果表简洁，又让客户端与评审使用同一解释。
为什么使用这个类型
string 使用固定代码便于校验和展示映射；int32 需要额外单位枚举且不易辨读。代码保持 tick、mm 等稳定形式，中文解释写在文档或界面。
为什么这样导出
server 目标字典校验登记处理器单位，client 生成属性解释和换算显示。展示按 tick_hz=60 换算秒，但不把服务器整数 Tick 参数重写成浮点秒。
合法值与填写规则
必填本版单位之一：stamina_per_second、weight_point、mm_per_tick、mm、hp、round、tick、stamina、bool、item、use；必须与登记 Stat 一致，不能自造秒或米的别名。
正确填写示例
medkit_ticks 的 Unit=tick：基础 120 Tick 在 60 Hz 为 2 秒；mul_bp=5000 后为 60 Tick。倍率参数 5000 不是 5000 Tick。
常见错误与后果
在 shot_ticks 的 add 中填 -1 并以为减少 1 秒，实际只减 1 Tick；将 mm 的 1600 当作 1600 米会误读投掷范围。
与其他字段的分工及取舍
Unit 定义计量尺度，Op 决定是否使用该尺度，ValueMode 决定绝对值或修饰值。未来更换模拟频率或尺度需要统一迁移来源与处理器，不只改显示文案。
06 AllowedOps合法运算 string server

限定每种属性允许使用的运算，阻止形式合法而语义无效的参数。

字段职责
限定每种属性允许使用的运算，阻止形式合法而语义无效的参数。
为什么需要这个字段
数值属性可以支持固定增加或倍率，但复活生命和体力从基础 0 计算，倍率作用于 0 没有意义；满血标记也只能 add=1。AllowedOps 让表格构建先拒绝这些错误，避免每个效果都要靠策划记住特殊语义。当前运算模块仅认 add/mul_bp，本列是迁移后属性校验的白名单，不允许新增字符串就扩出乘法、覆盖或脚本运算。
为什么使用这个类型
string 用半角竖线编码小型枚举集合，沿用工具可处理的类型；add|mul_bp 可读且易拆分。不能填 Excel 数组或带逗号的自由文本。
为什么这样导出
仅 server，用于构建与运行入口的权威校验；client 获得已合法的 Op 和 Value 用于展示，不需要携带完整的管理白名单。客户端如需编辑器校验，应另接工具流程。
合法值与填写规则
必填 add、mul_bp 或 add|mul_bp；无重复项、无空项、无空格，顺序建议固定为 add|mul_bp。absolute 和 flag 本版必须 add；效果 Op 必须属于本列。
正确填写示例
revive_hp AllowedOps=add；run_speed AllowedOps=add|mul_bp；revive_full_hp AllowedOps=add。
常见错误与后果
填 add,mul_bp 会违反竖线格式；把 revive_hp 配 mul_bp=15000，既不能给基础 0 提供生命，也违背现有复活只接受 add 的规则。
与其他字段的分工及取舍
AllowedOps 约束操作集合，ValueMode 说明参数性质，Value 仍需通用范围和最终值检查。未来新增运算必须先扩运算引擎、合成顺序及身份摘要契约。
07 ValueMode数值语义 string server

区分基础属性修饰、机制绝对参数和机制开关。

字段职责
区分基础属性修饰、机制绝对参数和机制开关。
为什么需要这个字段
同一 add 参数有三种不同意思：weight add=1 增加基础负重，revive_hp add=25 从基础 0 求出复活后的绝对生命，revive_full_hp add=1 开启满血覆盖。ValueMode 将这些语义写入属性字典，防止把复活理解成给死亡前生命加 25，或把标记理解成治疗 1 点。它是配套校验元信息，当前 skill.lua 仍通过 revive_ 等代码判断，迁移时需与登记规则一致。
为什么使用这个类型
string 使用 modifier/absolute/flag 三个明确枚举，避免多个布尔列形成不合法组合。字段不执行任意公式，不需要解析脚本文本。
为什么这样导出
仅 server，用于属性规则校验和正确投影；client 的面向玩家解释由 EffectDesc 与 Unit 表达，避免让普通界面用户承担内部模式术语。
合法值与填写规则
必填 modifier、absolute、flag；本版 12/13 为 absolute，14 为 flag，其余 modifier。absolute 只允许 add 且不得为负；flag 只允许 add=1；最终角色边界仍必须检查。
正确填写示例
revive_hp ValueMode=absolute，add=25 表示复活后生命 25；revive_full_hp ValueMode=flag，add=1 表示覆盖为最大生命。
常见错误与后果
把复活参数设 modifier 并以当前生命为基础，会得到错误复活结果；将 flag 的 Value 填 100 会被误当百分比且违反固定开关规则。
与其他字段的分工及取舍
ValueMode 解释单属性参数，Category 解释整体技能，Op 负责具体算术。未来覆盖值或条件开关需扩明确处理器契约，不能仅新增模式字符串便声称支持。

02 SkillIdx所属技能 ID int32 server/client

字段职责
把一条效果显式关联到对应的技能记录。
为什么需要这个字段

03 AttributeId目标属性 ID int32 server/client

字段职责
用外键选择效果修改的能力，替代重复填写自由 Stat 字符串。
为什么需要这个字段
属性字典已经维护名称、单位、对象和合法运算，效果只需引用 AttributeId，就能一次得到完整语义并验证对象一致。这样调整一个属性说明或合法运算时不必搜索所有效果逐行改字符串，也能在导出前发现引用缺失。本版将原 SkillEffect.Stat 改为 int32 外键，随后投影回现有 stat/op/value；这个转换当前尚未实现，不能直接改列名便期待原解析运行。
为什么使用这个类型

为什么这样导出
server 目标构建从字典查 Stat 与校验信息，client 按同一外键获取单位和名称。server/client 标记是新结构目标，旧 cfg_build.lua 仍读取 Stat，必须迁移。

与其他字段的分工及取舍
AttributeId 选择能力，Op/Value 选择修改方式与幅度，基础值仍在角色和装备表。本版同技能同属性只一条效果，未来组合固定量和倍率需先扩合成契约。
04 Op运算 string server/client

规定参数是固定增量还是万分比倍率因子。

字段职责
规定参数是固定增量还是万分比倍率因子。
为什么需要这个字段
固定增加 1 点负重和增加 20% 奔跑速度需要不同运算，不能凭数值大小自动猜测。现有 skill.lua 支持 add 与 mul_bp，同属性先汇总固定增量，再把各倍率相对 10000 的贡献相加，最后统一取整；显式 Op 使这一合成契约不受技能获得顺序影响。复活绝对值和满血标记仅接受 add，需结合属性白名单和模式解释，避免数学形式正确但机制无效。
为什么使用这个类型
string 保存现有代码认可的 add/mul_bp 枚举，可直接与 AllowedOps 匹配；不用符号 +、× 或数字 1/2，减少工具和策划之间的翻译。
为什么这样导出
server 执行运算和门禁，client 可正确解释效果比例与结果预览。客户端预览不能改变服务端统一汇总、取整和越界拒绝的顺序。
合法值与填写规则
必填 add 或 mul_bp，且必须属于所引用属性 AllowedOps；absolute/flag 只用 add。不得填 mul、percent 或公式；同属性倍率贡献相加，不逐条相乘。
正确填写示例
灵缇 Op=mul_bp、Value=12000 表示乘 1.2；军需官 Op=add、Value=1 表示增加 1 点负重。
常见错误与后果
把 Op 写 mul 会不被现有模块认可；按获得顺序把 1.2 和 1.5 相乘得到 1.8，会违背当前合成应为 1.7 的规则。
与其他字段的分工及取舍
Op 定义算术，ValueMode 定义绝对值或开关语义，Unit 定义 add 的单位。首版不支持 set、min、max 或任意公式，新运算需配套实现与内容版本校验。

6.3 怎样理解 add 和 mul_bp

写法 含义 例子
modifier + add=1 基础属性增加 1 个该属性单位 负重 3 变为 4
modifier + add=-10 基础属性减少 10 个单位 仅在该属性允许且最终值合法时使用
modifier + mul_bp=10000 保持原值 100%
modifier + mul_bp=12000 基础值乘 1.2 增加 20%
modifier + mul_bp=7500 基础值乘 0.75 减少 25%
modifier + mul_bp=5000 基础值乘 0.5 减半
modifier + mul_bp=20000 基础值乘 2 翻倍
absolute + add=25 机制绝对参数为 25 复活后生命为 25
flag + add=1 开启指定机制修饰 将复活后的生命覆盖为最大生命

mul_bp 使用万分比因子。减少 30% 填 7000，增加 30% 填 13000，不填 30、0.3 或 -3000。

同一属性按当前运算规则合成：

固定增量 = 所有 add 参数之和
倍率因子 = 10000 + 所有 (mul_bp 参数 - 10000) 之和
最终值   = floor((基础值 + 固定增量) × 倍率因子 / 10000)

多条倍率的贡献相加。两个不同技能分别增加 20% 和 50%，合成因子是 17000；两个分别减少 25% 的效果合成因子是 5000。不得按技能获得顺序逐条相乘。

同一个技能内，同一个 AttributeId 只允许一条效果。若一个技能需要同属性的固定量和倍率组合，首版应先重新设计为一条明确效果，或另行扩展合成契约。

Value 的通用输入范围沿用现有门禁：add 为 -1000000～1000000；mul_bp 为 0～100000。绝对复活参数不得为负，标记只能为 1，额外奖励次数不得为负。倍率合成后也必须满足最终值边界。

运算结果向下取整，越界时拒绝配置或整份配装，不自动截断。例如使用时间基础为 1 Tick 时再减半会得到 0，必须报错；应调整来源参数或效果值。

减半的是时间而非治疗量或工具消耗次数。对 1 Tick 来源值减半会向下取整为 0，应拒绝不合法配置，不能把 0 Tick 当成瞬发医疗。

验收场景

  • EffectIdx=1101 引用属性 11，mul_bp=5000，120→60 Tick。
  • 只作用 medkit，生命针剂的时长保持来源值。

这项技能提供什么选择

为什么采用这组初始参数

实际作用范围

验收场景

  • EffectIdx=1201 引用属性 9，mul_bp=20000，基础 50→100 生命点。
  • 当前 50/150 成功使用后为 150；当前 120/150 使用后也只到 150。

容易误解的地方

验收场景

  • EffectIdx=1301 引用属性 10，mul_bp=15000，炸药束 1600→2400 毫米。
  • 飞行速度保持 100 毫米/Tick，伤害与爆炸半径保持来源值。
  • 当前只作用 bomb，不为匕首、医疗包或未实现工具自动注册投掷行为。

14 开箱大师待扩展 · 建议禁用
crate_bonus_count / add / 1
这项技能提供什么选择
额外奖励属于猎人的箱子交互能力，而不是修改某种工具，所以使用 player/mechanic/passive。把基础奖励和额外奖励放在一次提交中，可以避免先领取基础奖励后因容量不足丢失加成，或重复请求复制物品；真实箱子来源还未补齐时，应保留规则而不捏造奖励 ID。
为什么采用这组初始参数

实际作用范围
作用对象为 player，类别为 mechanic，生命周期为 passive。仅适用于后续明确标识的道具奖励箱；当前 supply 是工具补给点，不能全部自动当成奖励箱。机制尚未实现，真实奖励来源待补充策划，Enabled 保持 0。
触发与消费时机

完整结果示例
独立机制夹具可验证基础 1 个加额外 1 个，共 2 个道具单位。两次抽取可得到同一道具，并按合法规则堆叠；如果是不同道具则分别占用对应容量。示例不定义生产奖励池或道具 ID。
容易误解的地方
推荐容量不足时整笔拒绝，不发基础或额外奖励，也不消耗箱子；失败还要保留随机状态，避免反复失败刷新奖励。迟到、重复请求、交互中断或终局请求不能再次发奖，不得借用已移除的怪物掉落表补造来源。

验收场景

  • EffectIdx=1401 引用属性 15，add=1；未实现处理器或缺少真实来源时保持禁用。
  • 独立奖励夹具验证基础 1 加额外 1，同道具合法叠堆与不同道具占用容量均正确。
  • 容量不足时物品、箱子状态和随机状态都不变，腾出空间后重试保持相同候选结果。
  • 同一箱子重复、迟到或中断交互请求不重复发奖；基础与额外奖励只有一次成功提交。
15 货运骡子待扩展 · 建议禁用
tool_capacity / add / 1
这项技能提供什么选择
用户已确认携带量指每种非消耗品工具的携带数量／可用次数，因此采用单种工具容量加成，不改变工具槽或背包格。将 CarryLimit 上限与 Quantity 初始化数量分开，可以让技能扩大可携带空间，同时不免费补发次数，也避免永久出战与结算复制库存。
为什么采用这组初始参数
配置 tool_capacity/add/1，增加 1 为建议初值，尚未经策划批准；适用口径已确认不等于数值已批准。急救包基础 Quantity=3、建议 CarryLimit=3，技能后容量为 4，能多容纳一次实际库存或补给恢复。固定加 1 可明确每一种适用工具的增量，避免小容量倍率取整没有收益。
实际作用范围
作用对象为 tool，类别为 numeric，生命周期为 passive。新增 Tool.CarryLimit，要求 1≤Quantity≤CarryLimit≤100；当前仅已实现的非消耗品次数工具急救包适用。匕首排除，针剂与炸药属于消耗品而排除；照明棒尚未实现，只列未来可纳入对象。
触发与消费时机
配装、初始化、补给、拾取、导入、永久出战和结算统一读取有效 CarryLimit。技能只修改上限，不直接增加当前 count 或永久库存；补给可在有效容量内恢复次数，资产结算按本局实际带入量和已有资产契约处理。
完整结果示例
急救包基础携带上限 3→4。普通独立夹具仍按 Quantity=3 初始化为 3/4；永久库存有 4 次时可带入 4/4，库存只有 3 次时仍为 3/4。未来照明棒基础 5 可在实现后变为 6，但当前不得启用该工具运行内容。
容易误解的地方
不能在获得技能时自动补发第 4 次，也不能把局内补给当成可永久结算的新增库存。永久结算要保存实际带入量，不能继续用旧基础 uses 代替；未来局中移除技能若当前数量超过新容量，应返回容量冲突，不静默删道具。

验收场景

  • EffectIdx=1501 引用属性 16，add=1；机制未实现前 Enabled=0，当前仅急救包进入适用集合。
  • 普通初始化为 3/4，实际库存 4 次可带入 4/4，库存 3 次仍为 3/4；获得技能不自动补次数。
  • 补给、拾取与导入使用同一有效容量；匕首、生命针剂和炸药容量不增加，未实现照明棒不进入运行内容。
  • 永久出战与结算按实际带入量验证，不复制库存；数量高于移除后容量时明确返回冲突。

四项待扩展技能的完整规则建议

8.1 精力充沛：先建立奔跑扣耗

角色表 RunCost 目前为 0，现有校验只接受 0，移动逻辑没有持续扣体力。仅填写技能效果 301 不会产生效果。

建议在角色表将 RunCost 的字段说明改为“奔跑每秒体力消耗”，调试基础值填 10。保持原类型 int32 和字段名，不扩大到跳跃体耗；本版 JumpCost 仍为 0。

建议扣耗规则：

  1. 仅在地面产生实际奔跑位移时扣耗，站立、撞墙不动、匍匐、爬梯不按奔跑扣耗。
  2. 每 Tick 累加有效每秒扣耗，累计值整除 tick_hz 后扣整数体力，余数保留到下一次实际奔跑；停止奔跑不能通过清除余数规避消耗。
  3. 扣耗余数与现有体力恢复余数分开。暂停不推进，恢复至满体力时可以清理扣耗余数，开始新的满体力周期。
  4. 体力归零后回到普通移动，开始现有体力恢复延迟。建议要求松开奔跑键后重新按下才能再次奔跑，避免一直按住时在恢复1点后反复切换。
  5. 新增扣耗余数和耗尽门禁的跨 Tick 状态由 C++ Player 保存，同步进入状态导入与恢复校验。

以 RunCost=10、tick_hz=60 为例，连续60个有效奔跑Tick消耗10体力；持有技能3后消耗7。RunCost=0 的来源配置即使乘7000仍为0，应提示该技能在该角色上无实际作用。

8.2 猫步：声音与视觉分别判定

推荐增加以下外部基础字段；这些是角色和怪物表的配套调整，不属于技能效果参数：

来源表 新字段 类型与标记 建议初值 单位/含义
Player WalkNoiseRadius int32，server/client 6000 地面普通行走声传播半径，毫米
Player RunNoiseRadius int32，server/client 10000 地面奔跑声传播半径，毫米
Player ProneNoiseRadius int32，server/client 2000 地面匍匐声传播半径，毫米
Monster HearingRange int32，server/client 10000 怪物听觉最大距离，毫米；0表示不听声

本版建议视觉条件为“在原 DetectRange 内且视线无遮挡”，听觉条件为“本 Tick 有行动声，且距离不超过行动声半径和怪物 HearingRange 两者的较小值”。两个条件任一满足即可获取目标。

猫步只将行动声基础半径乘5000。第一版行动声按二维圆形传播，可以穿墙，不模拟材料衰减。行走、奔跑和匍匐均按实际位移发声；站着不动不产生这三种行动声。跳跃落地、爬梯等其他声源后续另设基础规则，本版不自动归入该效果。

当前怪物感知是在 DetectRange 内直接警戒，没有独立听觉。因此实施猫步时必须同步修改感知入口。保留原无条件距离获取，再单独降低声音范围，不能验证出正确的潜行收益。

复活后现有新目标获取抑制门禁仍优先执行。枪声、爆炸声、视觉距离和警戒持续时间不受猫步倍率影响。客户端降低音量可作为表现调整，但不替代服务端半径规则。

验收示例：怪物DetectRange=6000、HearingRange=10000，玩家在8000毫米外奔跑时，无猫步可通过听觉发现，持有猫步时听不到；玩家在无遮挡的4000毫米处仍可通过视觉被发现。隔墙时，视觉应失败，再单独判听觉。

8.3 开箱大师：额外道具在一次提交中生成

本版技能14保持 Disabled，直到适用箱子和真实奖励来源接入。当前 supply 是工具补给点，不能自动把所有 supply 当成策划中的奖励道具箱。

推荐完整行为：

  1. 后续箱子配置标明是否属于适用道具箱，并绑定自己的奖励来源。技能只提供额外数量1，不指定怪物掉落表、道具ID或奖励池ID。
  2. 完成交互时读取猎人当前有效技能。先生成箱子基础奖励，再从同一箱子的奖励来源取得额外1个道具单位。
  3. “1个”定义为数量1，允许与基础奖励为同一道具并按合法规则堆叠；不是额外生成一整组随机数量，也不要求一定获得新道具种类。
  4. 形成包含全部物品变化和箱子已使用状态的候选，核对背包/工具数量及实体容量，再一次原子提交。
  5. 本版推荐容量不足时整笔拒绝：不发基础奖励、不发额外奖励、不消耗箱子。调整空间后可重试。失败还须保留随机状态，重试不能通过连续失败刷新奖励。
  6. 同一箱子本局只成功开一次；迟到、重复请求、交互中断或终局请求不再次发奖。

真实箱子资源仍待补充策划，不能在本版填写虚构奖励引用。机制可以用独立的奖励夹具验证基础1个＋额外1个、相同物品叠堆、不同物品占格及容量失败。

8.4 货运骡子：提升单种非消耗品工具容量

“携带量”的口径已由用户确认：每种非消耗品工具的携带数量／可用次数增加。本版按每种适用工具的携带次数上限实现，增加1为建议初值。当前工具表 ToolType=1 对应非消耗品工具，ToolType=2 对应针剂、炸药等消耗品。非消耗品工具的使用次数仍可能减少，并可由补给恢复。

推荐在工具表增加 CarryLimit，类型 int32、标记 server/client，单位为可携带次数；原 Quantity 保留为基础初始化数量。源配置必须满足 1 ≤ Quantity ≤ CarryLimit ≤ 100。

三表必须执行的校验

层次 必须检查
字段 固定字段和类型；整数不为空，不接受公式；Enabled只允许0/1
身份 各表主键唯一；Attribute.Stat唯一；稳定ID不能随意重编号
外键 每个SkillEffect.SkillIdx存在；每个AttributeId存在；无孤立效果
技能内容 每项技能1～8条效果；同技能同属性不能重复；资源缺失不影响纯服务端机制验证
对象 Skill.Target必须等于所引用Attribute.Target；Category和Lifetime符合该机制的约定
运算 Op在AllowedOps中；Value是合法整数；AllowedOps和ValueMode与登记处理器一致
机制组合 技能1生命/体力成对且为player/mechanic/once；技能2为player/mechanic/death且仅flag=1
能力 启用技能必须有真实已实现处理器；3/6/14/15未完成时拒绝Enabled=1

引用闭包 启用默认配装、技能物品等不得引用禁用技能；正式显式来源必须选入所需Skill、Effect和Attribute

建议的错误定位应包含工作簿名、工作表、源行号、主键和具体问题，例如“SkillEffect 第8行，EffectIdx=301，技能3尚未实现，不能启用”。

校验 Disabled 行只验证结构和声明参数，不执行尚未实现的业务；Enabled行不能通过忽略错误、默认填0或自动补测试数值继续发布。
